# aerospace-sidebar

A permanent, always-visible sidebar on the macOS main display that tiled windows never cover. AeroSpace reserves the screen strip; this project supplies the window that occupies it. The sidebar replaces macOS notification banners and NotifyMeHow: it intercepts native notifications and lists them, together with notifications pushed by the `aerospace-sidebar` CLI and `aerospace-sidebar://` URLs.

## Commands

Swift package (`Package.swift`) driven by `justfile`:

- Prepare development dependencies (Swift packages, `alerter`): `just setup`
- Build and relaunch the app bundle: `just run`. It quits NotifyMeHow first (`just quit-notifymehow`) so only one app hides banners. `just stop` quits the sidebar gracefully; `just bundle` only builds `.build/AerospaceSidebar.app` and `bin/aerospace-sidebar`; the bundle also carries the CLI at `Contents/Helpers/aerospace-sidebar`, signed before the bundle, so one release archive installs both (the dotfiles tool links its CLI from there).
- CLI: `just cli <args>`, agent mode `just cli-ai <args>` (the CLI's `run`/`run-ai` equivalents; `run` launches the app)
- Push sample notifications through every path (CLI, URL scheme, native `osascript`), one per severity, one with a web link in its body, plus native alerts with an action, an action menu and a Reply button (`alerter`, `brew install vjeantet/tap/alerter`, sent as Script Editor like `osascript`; each waits in the background until answered, closed or `alert_timeout` seconds pass), and banners from an app that declares notification categories (Notification Sampler, `Tools/NotificationSampler`: Approve, Reject (destructive) and Later, and Reply with a text field): `just test-notifications [alert_timeout]` (default 600). The sampler pushes each response back through the CLI as "Notification Sampler got <action>" (Open for a click, Dismiss for a close, the reply text as body) and quits once both are answered or closed, or after `alert_timeout` seconds, removing the rest. Its first run makes macOS ask whether Notification Sampler may post notifications; set its style to Alerts in System Settings › Notifications for the persistent variant. `open` gives the sampler no terminal, so its errors and the CLI's go to `.build/NotificationSampler.log`, which the recipe deletes before each run. `just sampler` only builds `.build/NotificationSampler.app`.
- No recipe makes macOS post a notification that only the notification database sees (delivered during a Focus, or from an app whose notification style is None): whether a banner shows depends on System Settings, not on the poster. To exercise that path, turn on a Focus or set an app's style to None (Notification Sampler's, for one) before running `just test-notifications`; CLI and URL pushes never reach macOS, so only the `osascript`, alerter and sampler notifications take that path.
- Fill the list with distinct notifications that never stack, to check scrolling: `just fill-notifications [count]` (default 20)
- Screenshot for the README: `just screenshot [output]` builds the bundle, quits the running sidebar (`Tools/Screenshot/screenshot-helper quit <pid>`, a quit Apple Event to that process only), opens a second copy in demo mode on `docs/screenshot/`, captures its panel window (`screencapture -o -l`), crops the transparent strip under the cards and opens the sidebar that was running again. The screen must be unlocked. Edit the cards in `docs/screenshot/notifications.json` and the look in its `config.toml`, then run it again and commit `docs/screenshot/sidebar.png`.
- Tests: `just test`
- Coverage gate: `just coverage`
- Take the app off a privacy list so it asks again: `just reset-accessibility`, `just reset-full-disk-access`, or both with `just reset-permissions`
- Replace the vendored sketchybar-app-font with a release: `just update-app-font <tag>` (downloads `sketchybar-app-font.ttf`, `icon_map.json` and `LICENSE`, writes the tag to `VERSION`)
- Release archives into `dist/` (what the release workflow runs): `just release-archives <version>`. Set `AEROSPACE_SIDEBAR_SIGNING_IDENTITY=-` for an ad-hoc build like CI; note that it replaces `.build/AerospaceSidebar.app`, so run `just run` afterwards to restore the Developer ID build.

CI (`.github/workflows/ci.yml`) runs ten focused `ArrivalScrollHostedTests` executions followed by `just coverage` on `macos-26` for pushes to `main` and pull requests, with `AEROSPACE_SIDEBAR_SCREEN_TESTS=1` so the tests that show windows on screen run too (Gotchas). `.github/workflows/release.yml` runs on `v*` tags: coverage gate, `just release-archives`, then `gh release create` with `AerospaceSidebar_<version>_darwin_arm64.tar.gz`, `aerospace-sidebar_<version>_darwin_arm64.tar.gz` and `checksums.txt`. CI has no Developer ID, so release builds are ad-hoc signed and users re-grant Accessibility after each update. The README's installation section depends on these asset names.

`just test` and `just coverage` pass `--no-parallel` to Swift Testing: concurrent AppKit/SwiftUI test setup can monopolize the main actor past hosted animation tests' deadlines. Keep the strict one-thread cooperative pool too; serial test cases do not disable concurrency exercised within a test. Focused CI repetitions use the same execution mode.

`just coverage` runs `swift test --no-parallel --enable-code-coverage`, prints `llvm-cov report` for the test binary, and fails when line or function coverage over `Sources/` drops below 90% or when any `Sources/**/*.swift` file is missing from the report. It excludes `.build/` and `Tests/`. Test targets depend on both executables so each `main.swift` is compiled into the report; they stay unexecuted, so keep them minimal.

Recipes run every Swift toolchain command (`swift`, `swiftc`) behind the `with_scratch_tmpdir` prefix, the private `_scratch-tmpdir` recipe: it points `TMPDIR` at a fresh `.tmp/swift.XXXXXX` directory and removes it when the command exits, including on failure or interrupt, because the toolchain leaves empty `TemporaryDirectory.*` folders in `TMPDIR`. Prefix new Swift toolchain commands the same way. SwiftPM keeps its lock files in `TMPDIR` too, including the one that stops two builds from using `.build` at once, so the wrapper holds `.state/swift.lock` with `lockf` in its place: concurrent Swift toolchain commands in one checkout wait for each other, but the other steps of concurrent recipes (`bundle`'s `rm`, `cp` and `codesign`) can still overlap. A bare `swift build` outside the recipes still locks in the global `TMPDIR` and does not wait for them. The wrapper runs the command in its own process group, so it answers SIGINT, SIGQUIT, SIGHUP and SIGTERM by sending SIGINT to that group (the one signal on which SwiftPM stops its compile jobs), waits for the group to exit, killing it after 40 seconds, and only then removes the scratch directory.

Always launch the bundle, not `swift run`. The bundle supplies the bundle id, `LSUIElement` (which AeroSpace relies on, see Architecture) and the `aerospace-sidebar` URL scheme. `just bundle` signs it with the Developer ID identity in `AEROSPACE_SIDEBAR_SIGNING_IDENTITY` (default `Developer ID Application: Alex Gorb (4XCZD8P4CJ)`); a stable identity keeps the Accessibility permission across rebuilds, while ad-hoc signing loses it every build.

Useful AeroSpace commands while developing:

- List monitors and their names (used in gap patterns): `aerospace list-monitors`
- Apply config changes: `aerospace reload-config`
- Regenerate the live AeroSpace config from dotfiles: `bash ~/.dotfiles/mac-apps/aerospace/select-config.sh <home|mobile|work>` (shell alias `aerospace-select`; restarts AeroSpace)

- `swift-argument-parser`: CLI parsing. It lists only direct subcommands, so groups hide children (`shouldDisplay: false`) and render the full tree as their `discussion` (`CommandTree`). Both libraries export a type named `TOMLDecoder`; import only one per file. Its keyed containers' `allKeys` holds only the keys the container's key type can be made from (`Key(stringValue:)`), so a fixed `CodingKeys` enum never sees unknown keys; `strictContainer` lists them through a key type that accepts any name (`AnyCodingKey`).
- `PermissionFlow` (jaywcjlove/PermissionFlow): every way the sidebar asks for Accessibility or Full Disk Access (the Permissions group's steps and the sidebar's Set Up… buttons) opens the privacy pane through `PermissionFlowController.authorize(pane:sourceFrameInScreen:)`, which shows a floating panel under System Settings from which the user drags the app into the list; status comes from its `PermissionStatusRegistry`. ## Architecture

macOS has no public API for reserving screen space (no AppBar or strut equivalent). Only the menu bar and Dock shrink `NSScreen.visibleFrame`, which native zoom and Sequoia-style tiling use. The design therefore splits responsibilities:

1. **Space reservation: AeroSpace per-monitor outer gap.** Tiled windows on the target monitor stop short of the strip:
   ```toml
   [gaps]
   outer.<side> = [{ monitor."<pattern>" = <sidebar-width + 5> }, 5]   # 5 = existing default on other monitors
   ```
   Monitor patterns use the same syntax as `workspace-to-monitor-force-assignment`: `main`, `secondary`, a 1-based left-to-right index, or a case-insensitive regex substring of the monitor name. The last array element is the fallback.

   The sidebar targets `monitor.main` (System Settings → Displays → "Use as: Main display") on the edge set by `[sidebar] side` (default `right`). `[sidebar]` in the app's `config.toml` is the single source of side and width; `SidebarPanelController` re-pins whenever they change. Never hardcode the width elsewhere and never derive it from the AeroSpace config. AeroSpace must reserve the same strip: the `main` entry of `outer.<side>` minus that side's trailing fallback equals the width, so the regular 5pt gap stays between the sidebar and tiled windows. `AeroSpaceConfigEditor.analyze` compares the AeroSpace config (located like AeroSpace does: `~/.aerospace.toml` or `${XDG_CONFIG_HOME:-~/.config}/aerospace/aerospace.toml`, error if both exist) with the saved `[sidebar]`: a missing or different strip on the sidebar's side, or a `main` strip on the other side, is a mismatch. On the sidebar's side only a leading `monitor.main` entry counts (`AeroSpaceConfig.Gap.certainReservedWidth`): AeroSpace uses the first entry whose pattern matches a monitor, and an earlier name, index or `secondary` pattern can match the main monitor. Settings › Sidebar says so when other patterns come before the entry (`Analysis.mainEntryWidth` holds the entry's width wherever it stands). On the other side any `main` entry wider than the fallback counts (`AeroSpaceConfig.Gap.reservedWidth`). The fix rewrites a managed block (`# >>> aerospace-sidebar …` to `# <<< aerospace-sidebar <<<`) that owns `outer.left` and `outer.right` inside the gaps table; it keeps other monitors' entries and both fallbacks, puts the `main` entry first on the sidebar's side and drops a strip-reserving `main` entry on the other. A config without the block has its `outer.left`/`outer.right` lines moved into one; the comment lines right above them and comments after their values move above the block. TOML forbids a second `[gaps]` table, and a separate `[gaps.outer]` table collides with `outer.top`/`outer.bottom` dotted keys, so the block holds only the two assignments. A missing float rule is appended with an `# Added by aerospace-sidebar` comment.

   `AeroSpaceSync.sync()` applies the fix unless the config already matches or is missing: at launch, whenever the AeroSpace config changes on disk (`FileWatchers` on both places AeroSpace looks and on a symlinked config's target, `AeroSpaceSetup.configsToWatch()`, re-resolved on every report; each watches its directory or, while that is missing, the nearest existing ancestor, and reports after 1 s without changes), and on every `[sidebar]` change (Save or a hand edit of `config.toml`). The target is resolved with `destinationOfSymbolicLink`, not `resolvingSymlinksInPath()`, which returns a symlink to a missing file unchanged. A watcher on the symlink follows the target file but not its directory, so a target removed and created again later is seen only through the target's directory. It queues a change that arrives mid-update, including during Update Config or Write Again, and reports the result as `AeroSpaceSync.message` in Settings › Sidebar. An edit AeroSpace rejected is remembered with the config text and sidebar it was made for, while it was the last attempt. Syncs skip that config until either changes, because AeroSpace would reject the same edit again and each restore would wake the watcher into a write/restore loop. Update Config and Write Again always try, and any later attempt forgets the rejection, since a rejection can be transient (a check made while AeroSpace restarted). Generated configs are edited too: a regeneration that drops the block is repaired after it.

   `AeroSpaceSetup.apply` keeps one backup (`aerospace.toml.bak`), with the config's permissions: atomic writes keep an existing file's permissions (measured with Foundation on macOS 26.6), so the config and `config.toml` keep theirs, but the backup is another file. A symlinked config is edited at its target (`URL.symlinkTarget`). Only while AeroSpace (`bobko.aerospace`) runs, because the CLI talks to the running app and a failed check would otherwise restore the original, it checks the config with `reload-config --dry-run --no-gui` before and after the edit, then reloads. AeroSpace reports some problems and loads the config anyway, such as an unknown key (only errors marked preventConfigReload block a reload), so only problems the edit adds restore the original. A problem counts as added when it is a blank-line-separated paragraph of the check's output (`ReloadConfigCommand` joins diagnostics with blank lines) that matches no paragraph of the original's check. Array indices (`gaps.outer.right[1]`) are ignored in the comparison, because the edit inserts and drops gap entries and so moves the problems of the other entries. An edit that leaves only old problems is kept and reported (`Outcome.updatedWithExistingProblems`). The config is read again after the first check, so a save made meanwhile is the one edited. The original is restored only while the file still holds the edit; a version saved during the second check is kept (`SetupError.rejectedAndReplaced`). The delegate creates `AeroSpaceSync` at launch and hands it to the Settings window, so tests must inject one with a temporary home (`makeAeroSpaceSync`, `AeroSpaceSync.fake`, `AeroSpaceSetup.forTesting`), or launching and sidebar changes would edit the real AeroSpace config. The dotfiles `base.toml` holds the same block, and `select-config.sh` keeps the generated config's block when it regenerates and writes atomically.
2. **Sidebar window: self-positioning, always-on-top panel.** AeroSpace cannot position floating windows from config, so the sidebar sets its own frame to the reserved strip on `NSScreen.screens.first` (the menu-bar screen, which is AeroSpace's `main`). It uses `visibleFrame`, the same rect AeroSpace pads with outer gaps. Window behavior:
   - Borderless `NSPanel` subclass (`SidebarPanel`) with `.nonactivatingPanel`, `level` one below `.mainMenu` (layer 23: above other apps' windows, the Dock and NotificationCenter's window at 21, below the full-screen window of the screenshot thumbnail at the menu bar's layer 24, measured on macOS 26.6, so the thumbnail in the bottom corner shows above the sidebar), except while System Settings is the frontmost app (`SystemSettingsFollower`, see PermissionFlow under Dependencies)
   - The panel sets `becomesKeyOnlyIfNeeded`, so a click makes it key only on a view whose `needsPanelToBecomeKey` is true: SwiftUI's text fields (`NSTextField`s) are, while `NSHostingView` says so for every point on it, so the content view is a `SidebarHostingView` that answers false for itself. A click on a card, a choice or a button thus leaves the keyboard with the app the user types in: once the panel had taken it, nothing gave it back while that app stayed active (a card's `open -b` of the app the user was in does nothing).
   - `SidebarPanel` overrides `canBecomeKey` to accept key status only while handling a mouse-down on the panel (`NSWindow.currentEvent`) or for the one call in which `takeKeyboard()` makes it key (`grantsKeyStatus`; tests record the `becomeKey` seam instead of keying a real window). `CardChoices` and the card's accessibility action ask for that through the `requestKeyboard` environment value when the user opens a reply field: VoiceOver opens it without the click that otherwise makes the panel key, and typing reaches only the key window. Once key, the panel stays key whatever `canBecomeKey` says later (measured on macOS 26.6). A field shown again, as when the list scrolls it back into view, asks for nothing, and the field takes focus only once after the user opened it (`ReplyDraft.focusRequested`), a turn of the main actor after it appears: focus set as it appears does not take (measured). Borderless windows refuse key status by default, so without the override clicks never focus the sidebar and keyboard input (text fields, shortcuts) never reaches it. An unconditional `true` steals keyboard focus: once launching finishes AppKit makes the first visible window that can become key the key window (`_sendFinishLaunchingNotification`), and it picks another when a key window such as Settings closes. `.nonactivatingPanel` lets it become key without activating the app. Keep both.
   - Settings (⌘,) and Clear All are compact round icon buttons (`ExpandingIconButton`) under the list in the bottom corner on the sidebar's screen edge, Clear All outermost: Settings, then Clear All from left to right on a right-hand sidebar, mirrored on a left-hand one; there is no header, and the notes and cards start at the top. Under the pointer a button widens into a capsule that shows its title beside the icon (away from that edge, so the icon stays put) and turns white. The title is always laid out beside the icon and the collapsed label is the icon's width pinned to the icon's side (`ExpandingLabelStyle`), so widening reveals the title in place while it fades in; inserting it would slide it in with the growing edge. `SidebarPanelContent` reads the side from `SettingsStore` in its body so the view follows side changes live. Each card's dismiss button is the same control, shown only while the card or the button is hovered, overhanging the card's top-trailing corner and opening its label leftward; on a card (`ExpandingIconButton.Surface.card`) it draws its card's severity tint (`NotificationSeverity.cardFill`) over the same material as Clear All and Settings, a primary label, no floating shadow, and sizes from `NotificationCard.dismissScale`. It sits outside the card's hover scale, which would put its edges between pixels, at `NotificationCard.dismissOffset` (the scaled corner, rounded to whole pixels), and is drawn as large as it looks on the scaled card. Icon button diameters are rounded to whole pixels (`ExpandingIconButton.diameter(_:typography:displayScale:)`). It casts `CardButtonShadow.dismiss` through `CardButtonShadowEffect`: a soft halo (2 pt blur, no offset) at all times and, under the pointer, a hard shadow 2 pt down that fades over its own `change` while the button widens on its own animation. It has no rim or outline: at its size a one-pixel line steps visibly around the curve. The saber border is switched off for now (`showsSaberBorder` environment value, default false) and kept for later use; its unused, disabled code is intentional, so do not report or delete it. Switched on, a hovered card or button traces its edge with `SaberBorder`: a faint outline, and a beam that runs once around it in `SaberBeam.duration` each time the pointer arrives, growing out of the outline's point nearest where the pointer entered while it fades in, and fading out as its head runs on past that point (`SaberBeam.fade`; `SaberBlade` is `Animatable` so the fade follows the animated head), so neither end of the lap looks cut off (`.saberBorder` keeps that entry in screen space, so a widening icon button does not move it), clipped to the shape, a pale core inside a glow of the severity's color or the system accent (a core in the color itself vanishes into a high or critical card's matching stroke). The beam is the outline trimmed by arc length (`SaberTrail`, `Path.trimmedPath`), so it keeps one speed on long and short edges; a conic gradient would crawl along the middle of a long edge and race through the corners. Reduce Motion leaves only the outline.
   - Clicking a card plays a press (scale down) and a release (`PressableButtonStyle`, sequenced by `PressSequence`): the press always finishes before the release starts, however fast the click. The action runs as the release starts, so the card's fade-out plays alongside it; a release outside the card cancels the action. Option held as the mouse goes up (`NSEvent.modifierFlags`) runs the style's `alternateAction` instead, which on a card dismisses it without acting, like its dismiss button; the card's VoiceOver hint says so whenever a click does more than dismiss. `NSApp.currentEvent` would name the mouse-up only while AppKit dispatches it from its queue, which tests cannot drive without deadlocking SwiftUI's mouse tracking, so tests pass `modifierFlags`.
   - `SidebarAppDelegate.makeMainMenu()` installs a main menu with only an Edit menu (Undo, Redo, Cut, Copy, Paste, Select All, sent to the first responder). An `LSUIElement` app shows no menu bar, but key equivalents such as ⌘C and ⌘V reach text fields only through main menu items, so without it Settings' fields ignore them. It has no Quit item, which would make ⌘Q quit from every Settings group.
   - Quit Sidebar lives in Settings › General (⌘Q while that group is shown) and calls `NSApplication.terminate`; `LSUIElement` apps have no menu bar, so this is the only in-app quit.
   - Launch Services activates the app when it launches it or opens an `aerospace-sidebar://` URL without `-g` (browser links, Shortcuts' Open URL, `open`). Nothing in the app needs to be active, and while it is, the app the user was typing in has no key window. `SidebarAppDelegate.applicationDidBecomeActive` therefore hands activation back through `ActivationYielder`: `NSApp.yieldActivation(to:)`, then `activate(from: .current)` on the regular app last in front other than this one. That app is tracked from `NSWorkspace.didActivateApplicationNotification`, starting from the frontmost app at launch. Accessory apps are passed over: launchers such as Spotlight, Raycast and Alfred open such URLs and close their window as they do, so activating one would again leave no key window. Without such an app, or when the system refuses the activation (`activate(from:)` returns false, as for an app that has quit since), the app calls `NSApp.deactivate()` and the system picks the next app. A click on the font or color panel leaves activation alone: they are the windows that activate the app (neither is a `.nonactivatingPanel`), and their fields need the app active to take typing. The check is whether the pointer is over either panel while it shows (`ActivationYielder.isPointerOverPickerPanel`, which creates neither shared panel), not a pressed mouse button, which may already be up when a busy main thread handles the activation. Tests pass an `ActivationYielder` with a private notification center and recording `handOver`/`deactivate`/`isPointerOverPickerPanel` seams; the defaults activate real apps.
   - `collectionBehavior = [.canJoinAllSpaces, .stationary, .fullScreenAuxiliary, .ignoresCycle]`
   - `hidesOnDeactivate = false`
   - The panel is nearly invisible (`isOpaque = false`, 1% black background, `hasShadow = false`): WindowServer passes mouse events through fully transparent pixels before view hit testing, so the backing keeps scrolling continuous across card gaps and margins. Cards and buttons draw on `.regularMaterial` with a soft shadow to separate them from what is behind: `floatingShadow()` for Clear All and Settings, and for cards a cut-out shadow (`cutOutShadows` with a `ShadowCaster` of `CardSilhouette`, the card's outline with its stack layers; `NotificationCard.shadowOpacity`/`shadowRadius`/`shadowOffset`). A shadow on the composited card is darkest right at its edge and shows through the edge pixels the card only partly covers, turning them darker than both the card and the background: a stepped dark ring around the corners, plainest over busy wallpaper. The cut-out casts it from a black copy one pixel smaller than the card, behind it, with the card's area cut out. The hosting view is the content view directly.
   - The panel is created on the strip (`SidebarLayout` in `SidebarPanelController.init`), not at `.zero`: SwiftUI lays the content out first at the panel's initial size, and from zero width the next animated model change (the interception status at launch) grew every card out of nothing while re-wrapping its text. The launch reveal is deliberate instead: on first appearance `SidebarView` scales its content up from `SidebarReveal.collapsedScale` (not 0: AppKit inverts the transform and asserts on a zero scale) out of its corners on the sidebar's screen edge, with `SidebarView.motion`; with Reduce Motion it only fades in. The notes, the cards inside the scroll view and the empty list's label grow out of the top corner and the buttons out of the bottom one, each scaling on its own (`RevealEffect`), never the list's scroll view: AppKit's scroll view, scaled while the lazy list measured its cards, scrolled itself 40–90 pt down and left the first card under the top fade (measured on macOS 26.6; the hosted test window does not reproduce it).

4. **Notification interception: Accessibility API on NotificationCenter.** `NotificationCenterMonitor` observes `com.apple.notificationcenterui` (`kAXWindowCreated`, `kAXValueChanged`, `kAXLayoutChanged`, `kAXFocusedWindowChanged`, and `kAXWindowMoved`, because NotificationCenter moves its window back to (0, 0) as the history panel closes; the sidebar's own moves report it too, and the sweep or history step that answers one moves nothing, since windows are moved only when they are not where they belong). Every event sweeps all of NotificationCenter's windows, never just the element the event names; sweeps repeat every 0.25 s while notifications are closing or stacks expanding, stop 1.5 s after the last event once settled, and give up 10 s after it. Observed macOS 26 behavior the code relies on, with the projects that report the same:
   - **One window.** Every banner and alert on screen sits in a single `AXWindow` titled "Notification Center" (subrole `AXSystemDialog`) under `AXHostingView` › group › `AXScrollArea` › group `AXNotificationListItems`. A banner arriving while another notification shows creates no window and only reports `kAXLayoutChanged` on itself (Tactile, SignalLadder).
   - **Subroles, matched exactly:** `AXNotificationCenterBanner` (temporary), `AXNotificationCenterAlert` (persistent), `AXNotificationCenterAlertStack`, `AXNotificationCenterBannerStack`. Other `AXNotificationCenter…` subroles exist, such as `…NextFocus` (AnyDoor).
   - **Stacks.** Persistent alerts from one app collapse into an `AlertStack` that exposes only the newest alert's texts and ends its description with ", stacked"; bursts posted milliseconds apart collapse the same way (SignalLadder). `AXPress` expands it into flat siblings: an `AXHeading` with the app name, `Confirm Show Less` and `Clear` buttons, and one `AXNotificationCenterAlert` per notification, each with its own UUID (macos-notification-cli, AriSweedler/dotfiles notif-center). The interceptor presses a stack at most once per 2 s (a second press collapses it) and handles the expanded alerts individually; stacks from apps in `apps_left_to_macos` stay collapsed. `BannerStack` groups entries in the history panel (OmniWM), described as "Stacked summary: " followed by the newest entry's app, title and body, or "…, from iPhone" for mirrored ones (measured on macOS 26.6; localized as `Stacked summary: %@` and `Stacked summary: %@, from iPhone`, `NotificationCenterLabels.stackedSummaries`), which `NotificationBanners.appName` strips so that `NotificationHistoryOpener` recognizes the card's app.
   - **History panel.** Opening Notification Center puts the history into the same window with the same subroles. The application element reports `AXExpanded` = true and the panel shows a button with `AXIdentifier` `widget-editor-button` (AnyDoor, OmniWM). While it is open the sweep touches nothing and moves hidden windows back; closing a history entry would delete it.
   - **Content.** Texts carry `AXIdentifier` `title`, `subtitle`, `body`, plus `header` and `date`, which are ignored (roycetech/applescript-core, talon-axkit). The `AXDescription` joins app name, title, subtitle and body; the app name is what precedes the exact texts (vorssaint-utils), else the first part. macOS's own notifications (Disk Not Ejected Properly) start with the title, get the source `macOS` and no click action. A description can lag behind its texts (a countdown body), so the exact match is not guaranteed. A notification whose title, subtitle and body all read empty (texts not populated yet, or AX calls timing out) is neither listed, hidden nor closed: it keeps its window on screen and the sweep stays pending until a later one reads it, because closing it would delete it before usernoted records it. One the sidebar already keeps hidden for its card, or is closing, needs no texts and stays in that care, so an empty read neither shows its window nor forgets it. A notification with only a subtitle is listed.
   - **Localized words.** Action names (`Close`, `Show`, `Show Details`, `Hide Details`), the description separator (`、` in Japanese) and the ", stacked" suffix are localized. `NotificationCenterLabels` reads them from `/System/Library/CoreServices/NotificationCenter.app/Contents/Resources/Localizable.loctable` for the application's `AXPreferredLanguage` (AnyDoor, MeetingMute, NotificationNanny); some table values are plural dictionaries, not strings. Raw action names look like `Name:Close\nTarget:0x0\nSelector:(null)`. A language read that fails, such as one timing out while NotificationCenter is slow after a wake, keeps the labels read before instead of falling back to English, which would leave every notification to macOS for its unknown actions; `NotificationCenterMonitor` reads the language again at each sweep until it succeeds.
   - **Interactive.** A plain notification offers only `AXPress` and the localized Show Details (Hide Details while its details are open), Show and Close. `NotificationBanners.needsInteraction` treats any other action, any control other than a close button or a button named like those actions (text fields, Reply buttons, Options pop-ups), and any element with `AXIdentifier` `action_button` (agent-desktop) as interactive. Hovering an alert adds Close and Show buttons to it (SignalLadder). Alerts are judged like banners, so an alert without choices is intercepted. An interactive notification whose choices a card offers is handed over to it (**Choices.**); for the others `actionable_left_to_macos` decides (Settings › Notifications › With buttons, "Keep banners with buttons cards cannot offer"): while it is on (the default) they stay native and are listed with `shownByMacOS`; when it is off they are hidden and listed without their buttons. When unsure, leave a notification native: losing its buttons is worse than seeing a banner.
   - **Kept, not closed.** Every intercepted notification with a UUID (banner, alert, and an interactive one while `actionable_left_to_macos` is off) is hidden but left open while a card lists its identifier (`SidebarNotification.nativeIdentifiers`, `SidebarModel.lists(notification:)`), so that the card can open it (**Opening**), and closed once the card is gone, like a notification with choices below. Closing would delete the notification and its click; Chromium reports a closed notification to the page. A hidden banner still times out into the history (vorssaint-utils, NotificationNanny), so intercepted banners stay in Notification Center's history like any other. A notification without a UUID cannot be found again and is closed, and so is one identified before without a card (listed by the database, or its card dismissed before a relaunch).
   - **Permission requests.** macOS asks whether an app may post notifications with an `AXNotificationCenterAlert` of its own (app `com.apple.notificationcenter.askpermissions`, title "“X” Notifications", Don’t Allow and Allow as named actions). Its Close answers Don't Allow: closing one logs `Authorization set for <app> to allow: NO` in usernoted and the app reads `.denied`. A card that goes away (dismissed, Clear All, expiry, `max_count`, a hiding rule) closes its notification, so `SystemNotificationInterceptor` checks `NotificationBanners.isPermissionRequest` before anything else and leaves such a request on screen, unlisted and never closed, remembering its identifier so the database does not list it either; `NotificationDatabaseMonitor` also skips that app's records. The check matches the localized title or body (`ALLOW_TITLE`, `ALLOW_BODY` and their `_CRITICAL` variants in `/System/Library/UserNotifications/Bundles/com.apple.notificationcenter.askpermissions.bundle/Contents/Resources/Localizable.loctable`, which `NotificationCenterLabels` reads in NotificationCenter's language); either is enough, since leaving a notification native by mistake costs little and missing a request denies an app.
   - **Choices.** An app's notification actions (Reply, Approve, Delete…) are named actions on banners and alerts alike, listed in reverse of the order the app declared them, and a history entry offers the same ones as the banner it was (measured on macOS 26.6). Named actions work while the window is off-screen and in the history panel, so a card can offer them for a notification the sidebar hides:
     - `NotificationBanners.namedChoices` reads them: every action besides `AXPress` and the localized plain ones (Show Details, Hide Details, Show, Close). It returns nil for stacks and for a notification that also holds a control other than a button for one of those choices or a plain action, such as an open reply field, a pop-up or another `action_button`; those work only on screen. Hovering a notification shows one choice as a button, which only duplicates the named action, and two or more under an "Options" menu button whose items are not in the accessibility tree. macOS 26's "Privacy & Security" alert, for one, exposes `AXPress`, `Name:Show Details`, `Name:Allow…`, `Name:Close` and no buttons.
     - What each choice is comes from the notification database (item 5, Full Disk Access): the categories each app declared, with each action's title, text input (placeholder and send-button title) and destructive flag. macOS writes a notification's record 5–7 s after delivering it, too late for a banner, so `DeclaredChoices.choices(ofApp:titled:)` matches the notification's named-action titles against its app's categories: the one category with exactly those titles gives the choices, in the app's order; no such category, or several that differ (one asking for text, one not), gives none. Each app's categories are cached for `DeclaredChoices.lifetime` (60 s); a read that fails keeps what was read before and is tried again after `DeclaredChoices.retryInterval` (5 s), and without Full Disk Access every app declared none. Cards the notification database lists (item 5) take their choices from the notification's own record instead (`NotificationDatabase.choices(ofNotification:)`).
     - Hand-over (`NotificationBanners.choices(of:labels:declared:)`, through `SystemNotificationInterceptor.offeredChoices`): a notification with a UUID, from an app not in `apps_left_to_macos`, whose app declared its choices (banners included, any number of choices), or else an alert with at most `NotificationBanners.maxChoices` (2) named actions, offered as plain titles in the app's order (NotificationCenter lists an NSUserNotification's actions reversed too, measured with alerter), is hidden but not closed whatever `actionable_left_to_macos` says, and listed with `SidebarNotification.nativeChoices` (identifier and `[NativeChoice]`). An NSUserNotification actions menu (alerter's `--actions a,b --dropdown-label X`) also lists its header as a named action just before Close, the localized Show by default or the app's label; performing it closes the alert without an answer, and nothing on screen tells it from a real choice. Such apps declare no categories, so their notifications' choices are known only from their records (item 5), which name a menu's items and tell its header apart. When Full Disk Access shows that the app declared no categories at all (`DeclaredChoices.declaresNone(ofApp:)`, false while they cannot be read), a notification whose choices nothing else tells (a banner's, or an alert's three or more, which every menu with a custom header has) and whose only controls are named actions is hidden for its card at once, without choices, rather than left on screen, where a banner would stay for its whole life (`SystemNotificationInterceptor.awaitsRecordedChoices`; Chromium browsers put a Settings button on every web notification). This covers only notifications whose record is still to come: one the database listed first had its record read already. Otherwise such notifications stay with macOS until usernoted records them. `NotificationDatabaseMonitor` reports the record's choices (`onChoices`), and the delegate lets the card that stands for that alert alone and lists it without choices offer them (`SidebarModel.offer(_:forNotification:)`: same id and place, no longer `shownByMacOS`; never for an app in `apps_left_to_macos`), then sweeps (`NotificationCenterMonitor.refresh()`). The interceptor then hands the alert over like any notification whose card lists its choices (`listsChoices`: its named titles, header included, while it holds no other control) and hides it. The menu's items are named actions on the alert (measured with alerter). The same upgrade gives a card its choices when NotificationCenter's titles matched several of the app's categories. Every other notification with choices keeps the interactive handling above. A notification whose card offers its choices keeps them while they remain named actions only, whatever the database says later.
     - `SidebarModel.offeredChoices(of:)` decides whether a card shows its choices. It needs `nativeChoices`, interception `.active` (not `.stopped`, which the monitor reports while it is stopped), the app's notifications not switched off (`notificationsAreOff`), and the notification not in `SidebarModel.unavailableChoices`. The interceptor reports that set through `onUnavailableChoices`. It holds three kinds of notification: a handed-over alert that left the screen without a step from the sidebar (alerts never go to the history); a handed-over notification that returned to macOS because it holds a control only macOS presents; and one whose choice the history no longer holds (`SystemNotificationInterceptor.choicesGone(of:)`, called by the monitor on `.absent`). A banner that times out keeps its choices, which its history entry offers. A sweep that finds a listed notification offering its choices again takes it out of the set, so a sweep that missed it (an accessibility call timing out, NotificationCenter restarting) costs the card its choices only until the next sweep. The set keeps only notifications whose cards list choices, and `SidebarView` animates its changes. A card that lists choices in the set says "Its buttons are no longer available" (`SidebarModel.hasLostChoices(_:)`, `NotificationCard.lostChoicesNote`) rather than dropping them silently; a card from a switched-off app has its badge instead. The set is not saved: after a relaunch every card offers its choices until performing one finds its notification gone.
     - Answering: `SidebarModel.choose(_:for:)` (choices without text input) and `reply(_:text:for:)` perform one answer at a time per card (`answering`; the card's choices are disabled meanwhile) and dismiss the card once performed; a refused or failed one keeps the card. `NotificationCenterMonitor.perform(_:on:from:completion:)`, which also handles card clicks as `.open`, performs the `NativeAction` where NotificationCenter shows or hides the notification (`SystemNotificationInterceptor.perform(_:on:in:)`: performed, refused or absent), else in the history (`NotificationHistoryOpener`, **Opening**: performed, refused, or absent when the history no longer holds it). `NotificationBanners.perform(_:on:labels:)` presses for `.open`, and for `.choice` performs the named action, which counts as done when it reports success or the notification's actions change: NotificationCenter reports `kAXErrorFailure` for a choice that opens a text field although the field is open before the call returns, and a gone notification has no actions.
     - Replies (`.reply(choice:text:send:)`): performing the choice opens the field (measured: the actions become `AXPress`, Hide Details, a send action named after the app's send title and Close; the children gain an `AXMenuButton` "More Actions…", an `AXScrollArea` › `AXTextArea` and an `AXButton` with the send title). The reply then sets the text area's `AXValue` and performs the send action, which delivers the text as a `UNTextInputNotificationResponse`. No step waits for the one before, on screen or off-screen in the history (measured). With no send title, the one action the field added sends. A reply that fails performs Hide Details, which closes the field: while a reply field is open NotificationCenter holds back every new notification (Gotchas).
     - Release: a dropped card (dismiss, Clear All, expiry, `max_count`) calls `notificationsReleased()`, which sweeps; the interceptor closes handed-over notifications no card lists, waiting `choiceGrace` (2 s) after a performed choice, a sent reply or a card click so the notification can leave on its own. A notification whose reply was sent still shows its field while it leaves, which reads as interactive; it stays hidden all the same, and so does every notification hidden with it. A card restored from `notifications.json` keeps its notification hidden after a relaunch. A notification whose card lists it without its choices is handled like any interactive notification: a card the database listed first from a record that names no choices, or one listed as shown by macOS while its app was in `apps_left_to_macos` (`listsChoices`, backed by `SidebarModel.lists(choicesOf:)`). While `actionable_left_to_macos` is on, such a notification stays native and its card going never closes it; while it is off, it is hidden without buttons and closed with its card. An alert whose undeclared choice turns out to open a reply field returns on screen whatever `actionable_left_to_macos` says: only macOS takes the typing.
   - **Opening.** A card click opens the newest notification its `nativeIdentifiers` name that NotificationCenter still has, as clicking it in macOS would. Only that tells an app which notification was clicked: a Chromium browser hands the click to the page (`onclick`, the service worker's `notificationclick`), where web Telegram focuses the tab and opens the chat, while activating the app only brings a window forward. `NotificationCenterMonitor.perform(.open, …)` presses a notification that is on screen or hidden (`SystemNotificationInterceptor.perform(_:on:in:)`; never a stack, which a press expands). Otherwise `NotificationHistoryOpener` opens it from the history, which is in the accessibility tree only while the panel is open; it performs a card's choices and replies there the same way (**Choices.**):
     - It presses the menu bar clock (`SystemAccessibility.menuBarClock`: the `com.apple.menuextra.clock` item of ControlCenter's `AXExtrasMenuBar` on macOS 26, of `com.apple.MenuBarAgent` one level down on later versions; AriSweedler/dotfiles notif-center, talon-axkit, OmniWM). The clock opens the panel on the main display and is ignored while the screen is locked.
     - It moves the panel's `AXSystemDialog` window off-screen as soon as the application reports `AXExpanded`. Measured on macOS 26.6: the panel can still show for up to about 50 ms first (seen when it opened on the built-in display), against 0.3 s unmoved. No prior art hides the panel; they all let it flash.
     - It presses the entry with one of the identifiers (or performs the request's `NativeAction` on it), after expanding stacks that carry one of them or come from the card's app (an expanded stack adds a heading with the app's name and Confirm Show Less and Clear buttons above its entries, measured on macOS 26.6; the opener presses only notifications, never Clear, which deletes the app's history): a collapsed stack carries its newest entry's identifier, and expanding turns that entry into an `AXNotificationCenterBanner` with the same identifier (OmniWM, SignalLadder). Pressing an entry delivers the click like a click on a banner: NotificationCenter logs `[<uuid>] notification clicked` and usernoted `Received response … <response action: contents …>` (checked on macOS 26.6 with alerter, Script Editor, Codex and Slack, whose own logs show `CLICK_NOTIFICATION` and the jump to the message). usernoted brings the app forward for every such response, and Electron drops a click it cannot match, so judge a click by the app's own logs or behavior, never by which window comes forward.
     - It presses the clock again to close the panel, unless pressing the entry closed it already: after performing, the step reads the panel's state again (NotificationCenter's elements are live), because a clock press after such a press would open the panel again. Measured on macOS 26.6, pressing an entry, a choice, or Reply and its send action leaves the panel open (over 1 s) until the clock closes it. A press the clock refuses may still have reached it (an accessibility call can fail or time out after delivery), and a second press that reaches it opens the closing panel again, so a refused press is repeated only once, `closeRetryDelay` (0.3 s) later while the panel stays open, and never by the step that finds the close out of time. The close gets `closeTimeout` (1 s) from the first attempt, however long the search took; a panel still open after that is left to the sweeps, which move it back on screen for the user to close. NotificationCenter moves its window back to (0, 0) as the panel closes, so every step hides the window first and the request ends `closeGrace` (0.5 s) after the panel reported closed; the observer's `kAXWindowMoved` answers that move at once. The window still shows at (0, 0) for 30–70 ms, with the notifications the sidebar keeps hidden for their cards (measured on macOS 26.6): NotificationCenter applies a move only once its own main thread, busy animating the panel closed, handles it, about 30 ms after its own move, so answering sooner, even from a thread of its own, does not shorten it. Meanwhile its steps replace sweeps, which would move the open panel back to (0, 0), and run every 20 ms (`historyStepInterval`). A panel the user opened before a request starts is neither moved nor closed; for one opened during a late-panel watch, see the next bullet.
     - It fails after `listGrace` (0.3 s) without the entry or a stack still expanding (Telegram closes its notifications once read), or after `timeout` (2 s); the card's own action (`activateApp`) then runs. Requests run one at a time, in the order they were started: a card clicked while another card's request runs, closing its panel included, waits for it and then opens the panel for itself, its `timeout` counting from then. NotificationCenter can take seconds to answer after a wake, so the panel may open after its request gave up: for `latePanelGrace` (2 s) a sweep that finds the panel open hands it back to the opener (`NotificationHistoryOpener.adoptLatePanel`), which hides and closes it instead of leaving it open on screen, and a request that begins meanwhile does not press the clock again, which would close that panel as it opens. NotificationCenter reports nothing that tells that panel from one the user opens meanwhile, so the user's recent input does (`RecentUserInput`, passed as `NotificationCenterMonitor(userInput:)`). `.system` reads `CGEventSource.secondsSinceLastEventType(.combinedSessionState, eventType:)`, which needs no permission (measured on macOS 26.6: an app without Input Monitoring, `CGPreflightListenEventAccess()` false, sees a key press's age), and leaves out input the sidebar received itself: a local event monitor (`ReceivedInput`, `NSEvent.addLocalMonitorForEvents`, which `NSApplication.sendEvent` calls) records when the app received its last left mouse down, key down and scroll, and an event type whose last session event came no later than that was the sidebar's (the window server's ages, read against `systemUptime`, place an event to within 0.1 ms, measured on macOS 26.6). A panel found open during the watch (by a sweep, by a request that began during the watch, or when the monitor stops) is the user's when, within `userInputWindow` (1 s) before, the user pressed the left mouse button with the pointer in a menu bar (the clock), pressed a key (a keyboard shortcut), or scrolled or made a gesture the Dock handles (dock control events, type 30, which `CGEventType` does not name). The user's panel ends the watch and is neither hidden nor closed, and a request that began during the watch uses it where it is. A click on a card is outside the menu bars, and the Return that sends a card's reply went to the sidebar, so neither counts. Trackpad gesture events (`NSEvent.EventType.gesture`) do not count: the trackpad driver sends one for any touch that makes no specific gesture, resting fingers included, so a card clicked on a trackpad would count. Whether the swipe in from the right edge reports as a dock control event or a scroll has not been measured. A screen's menu bar is the strip its visible frame leaves out at the top (30 pt, 32 pt beside the camera housing; `NSStatusBar.system.thickness` reports 22 pt, measured on macOS 26.6), or the thickness when the bar hides itself. A hot corner opens the panel on pointer motion alone, which tells nothing, so a panel opened that way during the watch is still taken for the late one and closed. So is one the user opens while NotificationCenter is slow, which is when panels open late: it may open more than 1 s after the click, when the pointer may have left the menu bar. A late panel that opens within 1 s of the user's input to another app stays open on screen, and so does a panel that opens after the watch. Stopping the monitor (quit, `replace_system` off) fails waiting requests and closes a panel the running one opened before moving NotificationCenter's windows back; after NotificationCenter exits the clock is not pressed.
     - A card from an app whose notifications are switched off (`SidebarModel.appNotificationsAreOff(for:)`, through `notificationsAreOff` from `AppNotificationsModel`, item 5) runs its action at once, and its VoiceOver hint says why (`SidebarModel.clickDescription(of:)`): NotificationCenter keeps such notifications with visibility `[]`, never as a banner or in the history, so no step finds them. A `SwitchedOffBadge` under its app icon (VoiceOver: the card's Allow Notifications action) switches them on as Allow in Settings › Notifications does (`SidebarModel.allowAppNotifications(for:)` through `AppNotificationsModel.allow(bundleIdentifier:name:)`, which takes usernoted's identifier for the card's), one app at a time (`allowingAppNotifications`); when the switch does not move, the sidebar shows what is left to the user in a note with Dismiss (`appNotificationsProblem`, from `AppNotificationsModel.switchOn(bundleIdentifier:name:)`); only installed apps' notifications have a bundle identifier, so such a card always has the icon. Switching the app on makes NotificationCenter list the notifications it kept, so their cards open them again.
   - **Hiding.** Position changes on notification elements are ignored, and Close only takes effect after the ~1.3 s slide-in; nothing hides a single banner. A window is moved to (-5000, -5000) only when every notification in it is intercepted, and the move is read back (vorssaint-utils). A window holding a native notification stays on-screen at `nativeOrigin`: the window covers the main display from (0, 0) at layer 21, below the sidebar's layer 23, and NotificationCenter draws notifications 16 pt inside the right edge of the visible frame (left of a Dock on the right, measured), so a right-side sidebar would cover them and take their clicks. The window moves left by the strip's width (`SidebarLayout.coverage(ofRightEdgeOf:)`), which keeps that 16 pt margin to the sidebar; NotificationCenter keeps that position and hit testing follows it until it discards the window, and the next window starts at (0, 0) again, so every sweep places it. `SidebarAppDelegate` sweeps again (`NotificationCenterMonitor.refresh()`) when the sidebar's side or width changes. Intercepted banners in that window stay visible until they time out, since the sidebar keeps them open for their cards. Windows moved off-screen or beside the sidebar are moved back to (0, 0) on attach, while the panel is open (unless `NotificationHistoryOpener` opened it) and on quit, so always quit with `just stop` (Apple Event quit) rather than `kill`, which skips `applicationWillTerminate`. Only the `AXSystemDialog` window (`NotificationBanners.isNotificationWindow`) is ever moved, by sweeps, `SystemNotificationInterceptor.restore` and `NotificationHistoryOpener` alike, so the sidebar never hides a window it would not move back: NotificationCenter also hosts the desktop widgets, whose windows sit on other displays at origins such as (-1920, 0) or (0, -1080) and must stay where they are.
   - **Closing.** Only an action named exactly the localized Close (or `AXCancel`), or a single close button, is used; two matches leave the notification alone (AnyDoor, MeetingMute). A substring match would press an app's own "Close Ticket".
   - **Identity.** Each notification's `AXIdentifier` is a UUID that survives stack expansion and NotificationCenter restarts (SignalLadder). Notifications with one are deduplicated by it alone, through `NotificationIdentities`; only those without one are compared by content within 10 s. Comparing identified notifications by content would drop real repeats, which `SidebarModel` stacks instead. `NotificationIdentities` keeps the newest 2000 UUIDs in `UserDefaults` (`notificationIdentities`), so a notification still on screen at a relaunch (left to macOS) is not listed again or stacked onto its card as a repeat, and a card dismissed before the relaunch stays gone. Tests pass `NotificationIdentities()` (memory only) or one using a fixture's memory-only preferences, never `.standard`, which `SidebarAppDelegate` defaults to.
   - **Permission.** The monitor never prompts for Accessibility (`AccessibilityPlatform.isTrusted()`); without it, it reports `.needsAccessibility` and the sidebar shows a Set Up… button (`SidebarAppDelegate.setUp(_:from:)`: Settings › Permissions plus PermissionFlow's step). It checks the permission every `permissionPollInterval` (2 s) while running, attaches once it is granted, and once it is taken away lets go of NotificationCenter (its windows cannot be moved back without the permission) and reports `.needsAccessibility` again; an attach after an exit or wake that finds it missing does the same instead of reporting NotificationCenter unavailable. Remove in Settings › Permissions calls `OnboardingModel.onPermissionsChanged`, which re-checks both monitors at once. Before removing Accessibility it calls `OnboardingModel.willRemoveAccessibility`, which stops the monitor while the permission still lets it move NotificationCenter's windows back: `tccutil` revokes the permission at once, and a window left off-screen would hide every later notification until NotificationCenter restarts. A monitor that was running reports `InterceptionStatus.stopped` as it stops, so cards offer no choices, which nothing could perform, until it reports again. Stopping one that was not running reports nothing, so `.disabled` stays. `SidebarAppDelegate.permissionsChanged` then starts the monitor again while `replace_system` is on, so it waits for the permission, or attaches again when `tccutil` failed.
   - **Lifecycle.** The monitor watches NotificationCenter's process for exit (`DispatchSourceProcess`) and reattaches with a doubling delay up to 30 s, because launch notifications missed relaunches (SignalLadder); it also reattaches after `NSWorkspace.didWakeNotification` (NotificationNanny). The observer's run loop source uses `.commonModes`, or events stall while a menu is open (SignalLadder), and AX calls time out after 1 s because NotificationCenter can take ~15 s to answer after a wake (NotificationNanny).
   - Focus/Do Not Disturb draws no banner at all; only the notification database (item 5) sees those notifications.

5. **Notification database: what no banner showed.** With Full Disk Access, `NotificationDatabaseMonitor` reads `~/Library/Group Containers/group.com.apple.usernoted/db2/db` read-only through the system `SQLite3` library and watches its `db-wal` with `FileWatcher`. Without Full Disk Access, opening it fails with `SQLITE_AUTH` ("authorization denied", `NotificationDatabase.Failure.accessDenied`; other failures are `.unreadable`); the monitor logs that once, reports `NotificationDatabaseStatus.needsFullDiskAccess` and retries every 5 s. A read that fails the same way while reading stops watching and retries too, so access taken away shows at the next write, or at once after Remove (`checkAccess()`). The sidebar shows a note with Set Up… (PermissionFlow's drag panel, like Settings › Permissions' Open Full Disk Access) and Dismiss; Full Disk Access is optional, so a dismissal is kept in `UserDefaults` (`fullDiskAccessNoteDismissed`, through `SidebarModel`'s `defaults`, which tests leave nil or point at a fixture's domain). macOS lists an app in Full Disk Access, switched off, once it has tried to open a protected file, so after the first launch the user usually only flips the switch.
   - Schema (Apple-private, read the same way by AriSweedler/dotfiles notif-center and OmniWM): `app(app_id, identifier)` holds bundle identifiers in lowercase (`com.vivaldi.vivaldi`), while usernoted's preferences, NotificationCenter, System Settings and `NSRunningApplication.runningApplications(withBundleIdentifier:)` use the app's own case (`com.vivaldi.Vivaldi`; measured on macOS 26.6), so queries by identifier use `COLLATE NOCASE` and `InstalledApps.app(bundleIdentifier:)` gives a listed card the app's own identifier: LaunchServices' `urlForApplication(withBundleIdentifier:)` finds the app in any case and its bundle declares the real one; `record(rec_id, app_id, uuid, data, delivered_date)` holds one row per notification. `uuid` is 16 bytes and equals the notification's `AXIdentifier` (OmniWM). `delivered_date` counts seconds since 2001 and is empty or in the future for scheduled notifications until usernoted delivers them (`UPDATE record SET delivered_date=…`). `rec_id` is `INTEGER PRIMARY KEY` without `AUTOINCREMENT`, so usernoted gives a new record the id of a newest record it deleted (an app withdrawing its notification, Clear All on kept alerts), and a scheduled record keeps the low id it got when it was scheduled: ids say nothing about delivery order. `data` is a binary property list whose `req` dictionary holds `titl`, `subt` and `body`, and names the notification's category in `cate` or carries an NSUserNotification's actions itself in `scat` (`id` `LEGACY`). `categories(app_id, categories)` holds per app a binary property list of the categories it declared, `[{id, acts: [{id, ti, op, st, tip, tia}]}]`: `ti` is the title, `op` the options (bit 1 destructive, as in `UNNotificationActionOptions`), and `st` 1 marks text input with placeholder `tip` and send-button title `tia`. `NotificationDatabase.declaredChoices(ofApp:)` reads an app's categories (item 4, **Choices.**). NSUserNotification apps declare none; their records carry their actions in `scat`. There an actions menu's items have `op` bit 64 (`NativeChoice.menuItemOption`), and its header, the action button (`id` `ACTION`), does not. When menu items are present, `NativeChoice.choices(declaredBy:)` leaves the header out, because performing it only closes the notification unanswered. It also leaves out actions without a title. `NotificationDatabase.choices(ofNotification:)` gives a record's choices: its `scat` actions (`DeliveredNotification.ownChoices`), else the actions of the app's category its `cate` names (`DeliveredNotification.category`), read fresh rather than cached.
   - Measured on macOS 26: usernoted writes a record to `db-wal` about 5–7 s after delivering it, so a notification without a banner reaches the sidebar roughly 8 s after delivery (that write, the watcher's 0.2 s debounce and the 1 s grace). A notification closed before then, which includes every banner the interceptor closes, is never written. The `database` log's "Read …" line gives both delays for each read.
   - Each new record waits 1 s for its banner, which is reported within about a second of delivery and so long before macOS writes the record; records whose UUID `NotificationIdentities` already holds are not listed. The choices they name go to `onChoices` instead (item 4, **Choices.**: a card listed without them may offer them). Each record's choices are read once (`choicesRead`), including a record a banner reported while it waited. The rest are listed with the app's display name and its own bundle identifier (`macOS`, no bundle identifier and no click action when no installed app has it), their delivery time, their UUID in `nativeIdentifiers`, so a click opens them from the history (item 4, **Opening**), and the choices their record names as `nativeChoices`, which the card performs in the history like any card's choices. This covers notifications delivered during Focus or Do Not Disturb, or with banner style None. A record whose choices cannot be read is listed without them, and the failure is logged.
   - Records are read by delivery date (`NotificationDatabase.notifications(deliveredAfter:by:)`), each read starting `NotificationDatabaseMonitor.lookback` (60 s) before the newest record read, because usernoted writes records seconds after delivering them and several at a time, so one can arrive after a record delivered later. A record read again is skipped while it waits for its banner, like one whose UUID `NotificationIdentities` holds. The read position is kept in `UserDefaults` (`notificationDatabaseDeliveredAfter`) and never moves past a record still waiting, so notifications delivered while the sidebar was not running, or still waiting when it quit or crashed, are listed at the next launch. The first launch starts from the newest delivered record (`latestDelivery(by:)`). A clock set back behind the read position or the newest record read moves the position back to `lookback` before the clock, and a record still waiting from before the setback waits out its grace from then.
   - Every connection waits up to `Connection.busyTimeout` (250 ms) for a lock usernoted holds before failing with `SQLITE_BUSY`. A read that fails other than with `SQLITE_AUTH` is tried once more `readRetryDelay` (1 s) later (`retryRead`): the write that woke it is spent, and its record would otherwise wait for an unrelated later write. The retry is not retried, a read that fails while it waits adds none, and the watcher keeps watching. A read that succeeds clears `lastError`, so a failure that comes back is logged again.
   - **Switched-off apps.** An app whose Allow Notifications switch is off (System Settings › Notifications) still has its notifications recorded here, the only place the sidebar sees them; usernoted logs `authorizationStatus: Denied` for them and NotificationCenter `notificationsAllowed: false`. They are listed only while `list_switched_off_apps` is on (default off, Settings › Notifications › Switched off): otherwise `SidebarModel.add` records them in `received`, which Settings › Notifications lists the apps from, and lists no card, and `SidebarModel.apply(listsSwitchedOffApps:)` turning it off drops the cards of apps switched off then. Whether an app is switched off is decided as a notification arrives, so cards from an app switched off later stay. usernoted's preferences (`~/Library/Group Containers/group.com.apple.usernoted/Library/Preferences/group.com.apple.usernoted.plist`, Full Disk Access; `com.apple.ncprefs` no longer exists) list each app in `apps` with `bundle-id` and `flags`, whose bit 25 (`NotificationPreferences.allowNotificationsFlag`) is the switch: the only bit that changes when it flips (measured on macOS 26.6). `AppNotificationsModel` reads that file at launch and again whenever usernoted writes it (`start()`, a `FileWatcher` on it; every `retryInterval`, 5 s, while it does not open, as without Full Disk Access), and keeps the switches as observable state that cards read as they draw, so a switch that flips in System Settings or through Allow updates their badges, clicks and choices at once. It compares bundle identifiers without regard to case, so cards saved with the database's lowercase identifiers count too, and Allow passes System Settings the identifier as usernoted keeps it. Settings › Notifications lists the switched-off apps that notified through macOS (`SidebarModel.received` entries with `nativeIdentifiers`; pushed ones name the app they were pushed from), read every second while shown, sorted by name and then `AppNotificationsModel.App.title`. A helper that posts under its app's name (Vivaldi Helper (Alerts), `com.vivaldi.Vivaldi.framework.AlertNotificationService`) has a switch of its own, so its row adds the installed app's own name (`installedName`, from `InstalledApps.app(bundleIdentifier:)`), which Allow's messages and VoiceOver label use too. **Allow** (`SystemSettingsNotificationSwitch`) opens `x-apple.systempreferences:com.apple.Notifications-Settings.extension?id=<bundle id>` and presses the `AXCheckBox` with `AXIdentifier` `allow-notifications`. A bundle identifier System Settings does not know leaves it on the page it showed, so it presses only on a page titled with the app's name and otherwise leaves the page to the user. The identifiers come from usernoted's own list, which System Settings knows, so the URL opens the right page even for apps that share a name (Google Chrome and its alerts helper are both titled "Google Chrome"). The pane's URL without `id` keeps the app page it shows, so it cannot go back to the list first (measured). Without Accessibility it only opens the page.
6. **Pushed notifications: two entry points with different trust.**
   - `aerospace-sidebar://notification/push?title=&subtitle=&body=&markdown=&severity=&open=&choice=&key=` (handled in `SidebarAppDelegate.application(_:open:)`). Any process, and any web page after the browser's confirmation prompt, can open it. Never let URLs carry commands, reply fields or asks; `open` accepts only `http`/`https`, and each repeated `choice` is one link choice, `TITLE=URL` split at the first `=`, its URL `http`/`https` only (`SidebarRequest.webURL`). `SidebarRequest.url()` refuses every other choice (`actionNotAllowedInURL`) and a title holding `=` (`equalsInURLChoiceTitle`), which would split differently. The sender app (Apple Event `keySenderPIDAttr`) labels the notification, else `URL`.
   - Control socket `$(getconf DARWIN_USER_TEMP_DIR)com.alexgorbatchev.aerospace-sidebar.sock`: mode 0600 in the per-user temp directory, peer uid checked with `getpeereid`, one `ControlRequest` per connection. Every message on it is one line of compact JSON (`UnixSocket.writeMessage`, which appends a newline; `MessageReader` splits at newlines, also takes what is left when the peer closes its side, and refuses a message longer than `UnixSocket.maxMessageSize` with `EMSGSIZE`, wherever its newline falls in a read). Clients never shut down their write side, because the server watches an ask's connection for the end of the stream. Only this path may carry `run` actions and choices that run commands or ask for text. Set `SO_NOSIGPIPE` on every socket (`UnixSocket.disableSIGPIPE`); a client that disconnects early otherwise kills the app. Accepted connections inherit it from the listener on Darwin, and the server sets it on them as well. The server replies `ControlResponse(error: nil)` from its socket queue as soon as a request decodes, which validates its fields, and passes `ControlRequest.validate()` (only an ask carries choices that answer, and an ask carries only those, at least one), and then hands the request to the main actor (`ControlServer.Request`) without waiting. The main actor can stay busy longer than the CLI's 5 s timeout (NotificationCenter after a wake), and a client that gave up would report a failure for, or resend, a notification the app goes on to show. `UnixSocket.exchange` throws `ExchangeError` by how far the request got: `tooLarge` (encoded past `maxMessageSize`, checked before connecting), `notConnected`, `notSent` (the server never read all of it) and `noReply` (sent in full, so the server may have it). `SocketNotificationSender` launches the app and retries only connect failures with `ENOENT`/`ECONNREFUSED` (`meansNoListener`), within `launchTimeout` (5 s). It never sends a request again once it was sent in full (`CLIError.noReply`, agent code `no_reply`). An ask is the exception to the warning that goes with it: the CLI closes an unconfirmed ask's connection, so the server either never hands it over (its reply fails) or withdraws its card on the hang-up, and `CLIError.askNotConfirmed` (also `no_reply`) says it can be asked again.
   - Asks (`ControlRequest.askNotification`, CLI `notification ask`): after the reply the server keeps the connection open as an `AskConnection` and writes one `AskAnswer` line (`answered(choice:reply:)` or `dismissed`) when the card is answered or goes, then closes it. The connection is non-blocking from then on, so a client that stops reading (a command suspended with Ctrl-Z) holds up only its own answer, which can be larger than the socket buffers, never the serial queue that accepts every request: a `DispatchSourceRead` on the server's queue watches the connection until the answer is due, and once it has let go of the descriptor a `DispatchSourceWrite` writes the answer as the client reads it. Meanwhile a read of zero bytes (or an error) means the client hung up, as Ctrl-C or the CLI's `--timeout` does by closing it, and the main actor's hang-up handler removes the card without answering (`SidebarModel.ask(_:asker:)`). `ControlServer.stop()` closes waiting asks, so quitting the app ends a waiting CLI with `CLIError.noAnswer` (`no_answer`, exit 1). `SidebarModel` keeps askers by card id outside the saved list; `settleAsks()`, run on every change and when a rule hides an arriving ask or the retention refuses it, answers `dismissed` to every asker whose card is gone, whichever way it went (dismiss, Option-click, a click on the card, Clear All, expiry, `max_count`, a rule). The CLI waits through `ControlConnection.answer(within:)` on a Dispatch thread (`SO_RCVTIMEO` per read, set from the remaining time); no answer exits 2 (`dismissed`, `timeout`, `CLIError.exitStatus`). The answer goes to stdout: the reply text or the choice title for people, `OK: ` and the `--json` object for agents (one line, whatever the reply holds), and the object alone with `--json` in both modes (`reply` is `null` for a choice without text). Cards restored from `notifications.json` drop their answering choices (`SidebarNotification.withoutAnswers`): their askers' connections are gone.
   - Pushed choices (`NotificationPayload.choices`, `PushedChoice`; CLI `--choice`, `--reply`, `--choice-link`, ask's `--choice`/`--reply`): a title and an action, `run` (login shell like a click's `run`, with `AEROSPACE_SIDEBAR_CHOICE` set to the title), `open` (`http`/`https` only, never asking for text) or `answer` (ask only), and `asksForText`, which opens the card's reply field; a `run` choice's text goes in `AEROSPACE_SIDEBAR_REPLY`. Values reach the command only through its environment (`NotificationActionPerforming.run(_:in:environment:)`, `Process.environment` merged over the app's), never its text. Cards show them through `SidebarModel.cardChoices(of:)`, a native notification's offered choices first, else the pushed ones as `NativeChoice`s (`PushedChoice.shown`: a text choice's field shows its title as placeholder and a Send button), so `CardChoices`, the reply field and the card's accessibility actions serve both. `choose`/`reply` perform a pushed choice at once and dismiss the card (an ask's through its asker); a reply is refused, and the field's send button disabled, past `PushedChoice.maxReplyLength` or with a NUL character (`PushedChoice.fits(reply:)`). `SidebarNotification.clickDescription` lists what each choice does, commands in full; an ask without a click action says a click dismisses it without answering. Run and link choices are saved with the card and keep working after a relaunch.
   - Field limits: `NotificationPayload` bounds every field, including the click action's URL (`maxOpenURLLength`, 8192), command (`maxCommandLength`, 4096) and working directory (`PATH_MAX`). Each limit applies in characters and also at `maxBytesPerCharacter` (4) UTF-8 bytes per character of the limit. A character can stack any number of code points (combining marks, emoji sequences), so a character count alone bounds neither untrusted URL input nor the socket message. Choices: at most `NotificationPayload.maxChoices` (8) with unique, non-empty titles of at most `PushedChoice.maxTitleLength` (64); their commands, working directories and URLs take the click action's limits, and a `run` choice needs a command. Values that reach a process (commands, working directories, choice titles, which go into `AEROSPACE_SIDEBAR_CHOICE`, and replies) refuse NUL (`SidebarRequestError.nulCharacter`): `Process` raises an Objective-C exception for a NUL in its arguments or environment, which aborts the app before `applicationWillTerminate` moves NotificationCenter's windows back. `WorkspaceActionPerformer.run` refuses one too rather than start the process. Valid fields can still encode past `UnixSocket.maxMessageSize` (each control character escapes to six bytes), and `exchange` refuses that before connecting (`too_large`).
   - Click actions: `open` (LaunchServices), `run` (the user's login shell from the user database, `getpwuid`, with `-lc`, in the CLI's working directory, output discarded), `activateApp` for intercepted and database notifications, which runs only when the card cannot open the notification it stands for (item 4, **Opening**). It opens the posting app through LaunchServices (`NSWorkspace.openApplication`, which launches it when it is not running), found by the card's `bundleIdentifier`, which `SidebarModel.activate` passes to `NotificationActionPerforming.perform(_:bundleIdentifier:)` instead of storing a copy in the action: a running app with that identifier first (two copies such as Xcode and Xcode-beta share one, and LaunchServices may prefer the other), else LaunchServices' copy; only without a bundle identifier is a running app found by name. An agent or background-only helper (`LSUIElement` or `LSBackgroundOnly` in its Info.plist, as a Boolean or a string) inside another app stands for the nearest app around it with a user interface (`WorkspaceActionPerformer.app(standingFor:)`): Chromium browsers post alerts from such a helper (Google Chrome Helper (Alerts), `com.google.Chrome.framework.AlertNotificationService`, which usernoted lists as an app of its own), while an app with a user interface inside another one, such as Simulator inside Xcode, is opened as it is. `NSRunningApplication.activate()` cannot launch an app, and since macOS 14 it is a request the system may decline from the never-active sidebar. Cards show no tooltip; their VoiceOver hint (`NotificationCard.helpText`) is `clickDescription`, including the full command.
   - Choices on cards (item 4, **Choices.**, and pushed choices above; shown while `SidebarModel.cardChoices(of:)` returns them): `CardChoices` shows one native push button (`ChoiceButton`) per choice inside the card's `PressableButtonStyle` button, wrapping onto more rows (`WrappingLayout`) where they do not fit side by side, a destructive one with the destructive role; they take their own clicks without pressing the card. A choice that asks for text opens a field under them (with the app's placeholder) and a send button titled with the app's send title, or the choice's title when it named none; Return sends, Escape or pressing the choice again closes the field, and nothing is sent empty. The card's `ReplyDraft` keeps the open choice and the text while the card shows. A stack gets a new card (see Stacking), which would drop them, so a card reports while a reply is typed on it (`NotificationCard.composingChanged`, `SidebarModel.setComposing(_:on:)`) and nothing stacks onto it, nor it onto another card. Choice buttons have capsule bezels (`.buttonBorderShape(.capsule)`) and cast `CardButtonShadow.choice` (the hard shadow only) under the pointer. `CardButtonShadowEffect` casts its shadows from a capsule behind the button with the inside cut out: a shadow (or `compositingGroup`, as in `floatingShadow()`) on a glass push button renders it into a layer of its own, where the glass has nothing behind it to blend with and turns black. VoiceOver sees each card as that one button and cannot press buttons nested in it: pressing one through accessibility runs the card's action instead. So the card's label children are ignored (each text would otherwise become an unnamed custom action), `NotificationCard.accessibilitySummary` is its label, the notification's choices, its body's links and Dismiss (shown only under the pointer) are its `accessibilityActions`, and the nested choice buttons are hidden from accessibility. A choice that asks for text opens its field through that action; while a reply is typed the card is no button (`NotificationCard.isComposing`) but the same face in a plain container, so the field and send button are controls VoiceOver reaches, which it cannot inside a button's label.
   - Links: web links written out with `http://` or `https://` in a card's body are links in its `Text` (`NotificationLinks`, `NSDataDetector` filtered to those schemes, since body text comes from any process and any web page and must not launch apps through their URL schemes; bare names like `deploy.sh` are not links; each text is searched once while it stays among the last `NotificationLinks.cacheLimit` searched, because cards evaluate their bodies on every hover change and `NSDataDetector` is slow). They keep the text's color (`.tint(.primary)`; plain links draw in the accent color) under a faint underline (`NotificationCard.linkUnderline`) that turns white while the pointer is on the link (`NotificationCard.hoveredLinkUnderline`). `Text` has no hover per link, so `LinkedText` builds the text from segments, marks each link's segment with a `TextAttribute` (`LinkedText.Link`, the link's character offset), tracks the pointer with `onContinuousHover`, finds the link under it in the laid-out text (`Text.LayoutKey`) and recolors that link's own underline, fading it in and out as the icon buttons fade to white (`Text` cross-fades its content when it changes inside an animation, and only the underline differs); drawing the underline in a `TextRenderer` instead would not match the one `Text` draws, which it snaps to whole points. The card's `openURL` action sends a clicked link to `SidebarModel.openLink`, which opens it through the performer and keeps the card; a link takes its own click like the choice buttons, so the card's action does not run.
   - Markdown: a push with `NotificationPayload.markdown` (CLI `--markdown`, URL `markdown=1`; saved with the card as `SidebarNotification.markdown`) has its body parsed by Foundation's `AttributedString(markdown:)` with `.inlineOnlyPreservingWhitespace` (`NotificationMarkdown`): bold, italic, code and strikethrough show styled, while lists, headings, tables and HTML show as written, so a card lays out no blocks. Links other than `http`/`https` with a host keep their text without the link, like bare text, and `NotificationLinks.linked` still links bare web URLs outside the markdown's links and code, then underlines every link. Code takes the configured font's fixed-width variant (`Font.monospaced()`) as an explicit run font instead of the `.code` intent, which SwiftUI draws in the system's fixed-width font. A link whose words differ in style spans several runs, each marked by `LinkedText` with where the whole link starts. VoiceOver, rules and the Rules pane's matches read `displayedBody`, the text without its syntax; field limits and stacking compare the markdown as written, with the flag.
   - Icons: `icon` (CLI `--icon`, URL `icon=`, at most 64 characters) is a sketchybar-app-font id, written `slack` or `:slack:` in any case. The font draws `:slack:` as one glyph through a ligature, so `AppIconFont.image(for:artwork:)` draws that text as a template image, centered on the glyph's outline bounds (`CTFontCreatePathForGlyph`): set as text it would sit off-center, because a ligature's advance is wider than its ink (142 points for a 100-point `:slack:`), and `CTLineGetImageBounds` uses the font's looser glyph boxes. `AppIconFont` checks ids against the bundled `icon_map.json`; an unknown id is not an error: the notification keeps no icon, stores the value as `invalidIcon`, and the card shows `Invalid icon: <value>` as a caption note styled like "Shown by macOS for its buttons". One id can stand for several apps (`mail`), so the VoiceOver label is the id in words, not an app name. Notifications from an app (intercepted or from the database) carry its `bundleIdentifier` instead, and the card draws that app's icon (`NSWorkspace.icon(forFile:)`, through the `appIcon` environment value); it is hidden from VoiceOver because the sender beside it names the app. A named font icon wins over the app's. Either icon fills a square at the card's top left (`LeadingIconLayout`), as tall as the header and the line under it set on one line each; every line of the card, notes and choices included, sits in the column beside it, so a wrapping title does not resize it. The square's height comes from each line's one-line ideal height, never from the width left beside the icon, which would feed wrapping back into the icon's size. Glyphs are set at `NotificationCard.iconArtwork` (824/1024, the app icon grid's artwork) of the square as their font size, and the vendored glyphs' ink fills at most the em, so they match an app icon's artwork. App icons from `NSWorkspace` carry a drop shadow in their margin; glyphs get the same one through `IconShadow` (25% black, blur radius 15 and 8 down per 1024 points of the square, measured on Notes, Calendar and Script Editor; Apple publishes no numbers), scaled to the square by a `GeometryReader`. SwiftUI's `VisualEffect` has no shadow, and a shadow drawn into the template image would take the template's tint. macOS finds the icon through the posting app's bundle identifier, but a banner's accessibility tree names only the app, so `InstalledApps.bundleIdentifier(named:)` maps the name back: a running app with that `localizedName` first (the poster usually runs), else an installed app in the application directories (two levels deep) whose Info.plist or Finder name matches. Name and icon lookups are cached per process, misses too. `notification push` sends the app it runs in as the payload's `bundleIdentifier` (`CLIContext.hostApp`): `__CFBundleIdentifier`, which macOS puts in an app's environment and its child processes inherit, else the terminal `TERM_PROGRAM` names (`CLIContext.terminalPrograms`; tmux names itself), skipping the sidebar's own identifier (commands run from cards inherit it) and apps LaunchServices does not know. Without one and without `--icon`, it sends the font's `terminal` icon. URL pushes and notifications macOS posts itself have no bundle identifier. The header marks only `open` actions with an SF Symbol (`link`); a command's card shows the app it was pushed from instead.
   - Severity `low` < `normal` < `high` < `critical`: the list sorts by severity, then newest first, and drops the least severe, oldest entries beyond `max_count` (200 by default). `low` is dimmed, `high` orange, `critical` red.
   - Rules: `[[rules]]` tables (`SidebarSettings.Rule`) hold `source`, `title`, `subtitle` and `body` patterns, case-insensitive Swift `Regex`es searched anywhere in that field (empty matches anything, at least one is required), and an `action`: `hide` or a severity. `SidebarModel.add` runs every arriving notification, from any entry point, through `NotificationRules` before stacking: the first rule whose patterns all match sets its severity or drops it. Saved rules also restack the listed cards (`SidebarModel.apply(rules:)`): each starts over from the severity it arrived with, which a card keeps in `postedSeverity` while a rule shows another, then goes through the new rules like an arriving notification, so it moves to its new severity, stacks with a card that now shows the same content (the stack keeps its first card's posted severity), or goes when a rule hides it. A notification a rule hides is never listed, so the interceptor closes it like any notification no card lists; a hidden notification left to macOS still shows its banner. Loading refuses unusable rules like any invalid setting (`rules[1].title: …`), Save names them (`Rule 2 …`). Settings › Rules shows the rules in a full-width list with +, −, ↑, ↓ along its bottom edge (the window is inactive, so no drag reordering is relied on) and an empty-state line, then edits the selected rule in a group box below: its patterns (each with a help tag naming what it matches, under a note on the pattern format), one Then pop-up (Hide it, or List as one severity) and which recently received notifications it matches (`SidebarModel.received`, so dismissed and hidden ones count too), in space reserved for `RulesPane.matchLines` lines. Without a selection the editor's rows stay laid out but invisible, disabled and hidden from accessibility under a line saying what to do, so selecting a rule never resizes the window. The list and the editor share one width (the pane's own, inside its margins); the editor is a group box in `SettingsGroupBoxStyle`, whose padding (`SettingsMetrics.groupPadding`) is known, unlike the system style's, and its fields take what that padding and the widest label (measured in the configured font) leave, so the padding is the same on the left, at the top and on the right. These widths are computed, not measured from the layout: measuring the box or the list fed back through the note's wrapping, the pane's reported size and the window's, and hung the app in a layout loop. Its note sets `SettingsHint(columns: 1)`: a grid without accessories gets an empty third column, and its gap, from a hint spanning two. AppKit controls without text of their own, such as the pop-up, have no baseline, so their row centers the label (`SettingsRow(alignment: .center)`).
   - Keys: a push may name its card with `NotificationPayload.key` (CLI `push --key`, `url --key`, URL `key=`; up to `maxKeyLength` (128), no NUL, not only whitespace; asks refuse one, `keyOnAsk`, since they never stack). It is saved with the card (`SidebarNotification.key`). `SidebarNotification.stacks(with:)` stacks two keyed entries with the same key and source whatever their content, and an unkeyed one only by content with another unkeyed one. Keys are scoped by source so a web page's URL (sourced by the opening app) cannot take over a CLI card (`aerospace-sidebar`). A keyed stack takes the newer push's content (`stacking(_:)`), counts it in `occurrences` and moves up as the newest like any stack; a card on which a reply is typed takes none, and a rule that hides a keyed push leaves the listed card as it was. `received` folds keyed pushes the same way, one entry per key holding the newest content, so Settings › Rules tests rules against what the card shows.
   - Stacking: `SidebarModel.add` folds a notification into a listed one with the same content (`hasSameContent`: source, `bundleIdentifier`, title, subtitle, body, `markdown`, severity, icon, `invalidIcon`, action, `shownByMacOS`, `nativeChoices`, `pushedChoices`, so cards for different alerts never stack; two asks never do, each answers its own asker, and neither does a card on which a reply is typed). The entry keeps its id, takes the newer `receivedAt`, adds `occurrences`, stands for both cards' native notifications (`nativeIdentifiers`, newest first, at most `SidebarNotification.maxNativeIdentifiers` (20); older ones are released like a dismissed card's, so the next sweep closes those still hidden), and is re-inserted as the newest. `SidebarView` keys cards by id and `occurrences`, so a restack fades the old card out and inserts a new one instead of sliding it across the translucent cards between. This is separate from the interceptor's 10 s dedupe, which drops NotificationCenter's repeated reports of one banner; stacking counts real repeats.
   - Scrolling: the list hides the system scroller (`.scrollIndicators(.never)`; `.hidden` still shows legacy scrollers when a mouse is attached) and draws `ScrollIndicator` in the margin on the sidebar's screen edge (`SidebarView.screenEdge`, shared with the buttons) from `onScrollGeometryChange`, dragging through `ScrollPosition`. The scroll geometry changes on every frame of a scroll, so it lives in `ListScroll`, an observable that only `ListEdgeFade` and `ListScrollIndicator` read: in `SidebarView`'s state it made every frame evaluate the list again, and every visible card with it, whose closures SwiftUI cannot compare, which kept a core busy while scrolling. Legacy scrollers draw a track and take their width from the cards. The list runs to the bottom of the visible frame and fades its top or bottom 48pt (`EdgeFadeMask`) while cards are hidden past that edge; scrolled to the end, `contentMargins` keeps 16pt under the last card. A notification that arrives and is listed (`SidebarModel.arrivals`, which only `add(_:)` changes, so restoring, rules, pruning and dismissals scroll nothing) scrolls its card into view, whole and clear of the edge fades, with the least scrolling (`ArrivalScroll.offset(showing:isLast:from:visibleHeight:)`): the first card shows at the top with the room above it for its dismiss button, the last at the end with its margin. Several arrivals in one main-actor turn, such as a batch the database lists, reach the view as one change, so it shows the top-most of their cards, the most severe and newest. The list is lazy and reports an arriving card's frame only after `onChange` has seen the arrival (measured on macOS 26.6), so until then it scrolls to the card by its `ForEach` identity, which brings it in at an edge, and the card's frame then sets the offset. `.scrollTargetLayout()` is left off: with it the top edge rests on the first card's top and hides the room above it. Nothing scrolls while the user is on the list (`SidebarActivity.isUsingList`): the pointer is on the panel (`SidebarPanel.hasPointer`: where a click would reach it, gaps between cards included and windows above it excluded, `receivesClicks(at:)`, or dragging from a press on it), a reply is being typed on a card (`ComposingReplyKey`), or the user's scroll is still going (`ScrollPhase.isUserScrolling`); a scroll the user starts cancels one waiting for a card's frame. The first card needs no frame (the top of the list) and neither does the last (`ArrivalScroll.Step.end`). With Reduce Motion the scroll jumps. The cards animate into place, with Reduce Motion too, and the content grows with them, so a scroll to a place (an offset or the end) can stop short of it; it is made again once that change has finished (`ArrivalScroll.layoutMoved(_:isUsingList:)`).
   - History: `SidebarModel` saves the list through `NotificationStore` on every change (`FileNotificationStore`: `~/Library/Application Support/com.alexgorbatchev.aerospace-sidebar/notifications.json`) and drops notifications older than `retention_hours` (24 by default) on load and every minute, so a relaunch restores the list. `add` refuses a notification already older than that (a database record from before a long quit), which would otherwise push newer cards past `max_count` until the next prune. It also keeps `received`: every notification as it arrived, before rules, newest first with repeats stacked, also after its card was dismissed or cleared or a rule hid it, under the same retention and `max_count`, saved to `received.json` beside the list. Settings › Rules tests rules against it, so a notification the user closed still shows what a rule would do to it. `FileNotificationStore.load` leaves out (and logs) entries that do not decode, such as ones another version wrote, instead of losing the whole file; the next save drops them. Tests pass an in-memory store; `SidebarModel` has no default store so tests cannot write the real file, and without a `receivedStore` it keeps `received` in memory.

7. **Settings.** `${XDG_CONFIG_HOME:-~/.config}/aerospace-sidebar/config.toml` holds `[sidebar] side (left|right), width (150…1000)`, `[notifications] replace_system, actionable_left_to_macos, apps_left_to_macos, list_switched_off_apps`, `[history] retention_hours (1…720), max_count (10…2000)`, `[font] name, size (8…32)`, `[background] color (#RRGGBB), opacity (0…1)` and `[[rules]]` (below). `SettingsStore` watches `config.toml` through `FileWatchers` (writes in place and atomic replacements alike, and a symlinked file's target too, so a target removed and created again, as a dotfiles checkout does, is seen). `SettingsFile.save` writes atomically at a symlink's target (`URL.symlinkTarget`, also when the target is missing), so a `config.toml` linked from a dotfiles repository stays a link; an atomic write at the link itself would replace it with a file and applies valid edits live; an invalid file keeps the last valid settings and surfaces `loadError`. Every table (`SidebarSettings`, its `Sidebar`, `Notifications`, `History`, `Font` and `Background`, and each `Rule`) decodes through `Decoder.strictContainer(keyedBy:)`, which refuses keys outside its `CaseIterable` `CodingKeys` with a `DecodingError.dataCorrupted` at the table's path, such as `rules[0]: unknown key titel; expected source, title, subtitle, body, or action` or `unknown key notification; expected sidebar, notifications, history, font, or rules`. A misspelled key or table therefore makes the whole file invalid, like a syntax error or an out-of-range value, instead of leaving its setting at the default (a rule with `titel` would otherwise hide everything from its source). At launch there are no last valid settings, so an invalid file means every setting takes its default: the sidebar sits on the default strip, and `AeroSpaceSync` reserves that strip in the AeroSpace config until the file loads again, when the `[sidebar]` change syncs it back. `SettingsStore.loadProblem` says which settings are in effect meanwhile (the previous ones, or the defaults when nothing valid has loaded since launch); the sidebar shows it in a note whose Settings… button opens General, which shows it under the settings file, and the Settings status line shows it too. A new setting needs only a case in its table's `CodingKeys`; a new table type must decode through `strictContainer` as well. A successful save clears `loadError`. An update writes the settings even when it changes nothing, while the file does not hold them because a save failed or the file does not load, so `saveError` tells whether the settings in memory are on disk and a second Save replaces an invalid file. Launch at login is never stored there: macOS owns that state, and a stored copy would re-enable a login item the user turned off in System Settings.
   - The Settings window has a full-height sidebar of groups (`SettingsGroup`: General, Appearance, Sidebar, Permissions, Notifications, Rules, History) beside the selected group's pane, like System Settings, and no section headers. Settings opens on General from the gear button and on Permissions from the sidebar's Set Up… buttons (`SidebarAppDelegate.setUp(_:from:)`, which also starts the step). The delegate owns the one `OnboardingModel`, made on first use, and hands it to Settings. `NSSplitViewController` holds a sidebar item (a SwiftUI `List` with `.listStyle(.sidebar)`, fixed at `SettingsMetrics.sidebarWidth`, not collapsible) and the panes in an `NSTabViewController` with `tabStyle = .unspecified`, which switches them. `SettingsNavigation.selection` is the shown group: the list binds to it and the controller follows it, selecting the pane and titling the window after the group. The selected row names the pane, so the window draws no title (`titleVisibility = .hidden`, no title bar separator, `titlebarAppearsTransparent`, no toolbar; the split view otherwise draws a title bar background with a separator line over the panes, which the window's separator style does not remove); the title stays for VoiceOver and the window list. The window uses `.fullSizeContentView`; `BelowTitleBarController` frames the panes in its safe area (frames, not constraints, which would tie the window's size to the shown pane's). The list's rows use `[font]` through `SettingsSidebarLabelStyle`, and its width scales with `Typography.scale`: the sidebar style sizes its own icon column for the system's sidebar font, so a row in another font needs the style's icon column, sized in multiples of the font size (`sidebarIconWidth`, `sidebarIconSpacing`), to keep its icons aligned. Each pane copies the layout of simple-ptt's settings window (`src/settings_window` in github.com/alexgorbatchev/simple-ptt): a grid with right-aligned `Label:` cells, subheadline-style secondary hints under controls (13pt and 11pt at the default font size), 8pt spacing, 20pt margins, checkboxes rather than switches, 80pt number fields with `Stepper` arrows (at the default font size), and, on the groups that edit `config.toml` (Appearance, Sidebar, Notifications, Rules, History), a separator + status line + Cancel/Save bar; General and Permissions act immediately, so they have none. Sidebar also holds the AeroSpace rows (`AeroSpaceRows`: config file and the Update Config step), with no header between them; those act immediately on the saved side and width. Notifications also lists the apps whose notifications are switched off (`SwitchedOffAppsRows`), whose Allow acts immediately too. Permissions holds everything the sidebar asks macOS for (Accessibility, Full Disk Access, launch at login), each with a hint saying whether it is required and why, and a Remove button beside its step: `tccutil reset Accessibility|SystemPolicyAllFiles <bundle id>` for the privacy permissions (always shown, since an entry macOS no longer recognizes after an update reads as not granted), `SMAppService.unregister` for the login item. General holds the settings file and Quit. The draft panes share one `SettingsEditor`, so Save on any of them saves every group's edits. Setup steps (Permissions, AeroSpace) start with a status circle (green `checkmark.circle.fill` when done, empty `circle` otherwise) followed by the step's button while not done; a finished step shows the checkmark alone. Edits stay in `SettingsEditor.draft` until Save; Cancel and closing the window discard them, but opening Settings again while it is open (gear, Set Up…) only switches groups. The draft font and background are the exception: they are previewed immediately through `SettingsStore.preview(font:)` and `preview(background:)` (in memory only, never written to `config.toml`), and Save or Cancel ends the preview. The draft remembers where it started (`start`), table by table: font and background (Appearance, named once in the warning when both changed in the file), sidebar, notifications, rules and history. Groups without edits follow changes to `config.toml` as they arrive. Save writes only the edited groups over the current settings. A group changed both in the draft and in the file, or a file that no longer loads (with or without edits), is replaced only by a second Save after a warning in the status line. The status line shows a load failure as soon as the file stops loading.
   - Unlike simple-ptt, which switches to the `.regular` activation policy while Settings is open, Settings is a non-activating `NSPanel` at `SettingsWindowController.level`, one above the sidebar's `SidebarPanelController.level`, so it stays above other apps' windows and the sidebar until closed, ordered in front with `orderFrontRegardless()`. Opening it from the closed state centers it on the sidebar's screen (`SidebarPanelController.primaryScreenVisibleFrame`); `NSWindow.center()` would use `NSScreen.main`, the screen with keyboard focus, which an app that never activates does not control. Size changes keep it centered until the user moves it, then keep its top edge. While it is open, opening it again leaves it where it is and keeps the unsaved draft. The exception is System Settings, where the Permissions steps send the user: while it is the frontmost app, `SystemSettingsFollower` drops Settings (and the sidebar) to the normal level and orders it behind, so it does not cover the permission lists and their switches, and raises it above the sidebar again when another app comes forward. A level change alone keeps the window's place in the stack, so both orderings are explicit. Switching the policy would make AeroSpace re-classify the sidebar panel as a window (see item 3), and `NSApp.activate()` from a background app is only a request since macOS 14. An `NSPopUpButton` opens in Settings while another app is frontmost (checked with a real click on the Rules pane's Then pop-up). SwiftUI's menu and segmented `Picker`s draw through AppKit without passing a font on, so they stay in the system font whatever `[font]` says; `PopUpPicker` wraps `NSPopUpButton` and sets the button's and its menu's `font`.
   - Background: `[background]` fills the sidebar's strip from the top of the screen to the bottom, behind the transparent menu bar too, in `color` at `opacity` (0, the default, shows none). `SidebarBackground` is a borderless, non-activating panel that ignores the mouse, at `SidebarBackground.level`, just below the Dock: above every app's windows, floating ones over the strip included, and under the Dock, the menu bar and the sidebar panel. While System Settings is in front it goes behind with the panel, at `.normal` just below it (`SystemSettingsFollower.onFollow`), so it covers neither System Settings nor the cards. `SidebarPanelController` frames it with `SidebarLayout.fullHeightFrame(in:of:)` (the strip's columns over the screen's full frame, `targetScreenFrame`) whenever it pins the panel, and on `SettingsStore.observeBackground`, which reports Settings' preview too. Picked colors are kept as sRGB (`SidebarSettings.RGBColor(_:)`, clamped to whole steps of 1/255).
   - Fonts: `[font] name` is a font family as Font Book lists it (empty = system font) and `size` is the body size. `Typography` derives every text style from it, keeping each `NSFont.TextStyle`'s proportion to `.body` (and its bold trait), so the default 13pt reproduces the system styles. `.typography(store)` on the sidebar's and each Settings pane's root view reads `SettingsStore.font` (the preview while Settings edits the font, else the saved font; `observeFont` reports its changes), clamps the size to the valid range, publishes `\.typography` and sets the body font for unstyled text and control labels; views pick other styles with `typography.font(.callout)` and friends instead of SwiftUI's `.font(.callout)` or fixed sizes. Settings › Appearance › Choose… opens the macOS font panel through `FontChooser`, which makes itself `NSFontManager.target` (the default target is the key window's first responder, which this app rarely has), sets the panel's `hidesOnDeactivate = false` (the window server keeps hide-on-deactivate panels off screen while their app is inactive, although AppKit still reports `isVisible`), places it beside Settings on the side away from the saved sidebar side, or the other side when that does not fit (AppKit's default position can be off-screen, and the sidebar floats above the panel), limits the panel to collection/face/size, and writes the picked family and size into the draft; the system font's hidden family (`.AppleSystemUIFont`) becomes an empty name. A family that is not installed renders the system font (SwiftUI's `Font.custom` would silently fall back to Helvetica), and Settings reports it. On font changes the Settings window runs `layoutSubtreeIfNeeded()` on its panes, shown or not, because pending SwiftUI updates only apply during a layout pass, so each pane reports its size for the new font.

It measures what the window adds around the panes and the list (title bar, toolbar, sidebar and its margins, which differ between macOS versions) from the current layout, which takes a window larger than those: assigning `contentViewController` shrinks the window to the empty split view, so `init` sets `measuringSize` after it. Measuring a degenerate window moved Settings off its screen. Each pane's root is `SettingsPaneHost<Pane>`: with the environment closure in the hosting controller's generic arguments, `NSStringFromClass` returns nil for it and `NSTabViewItem(viewController:)` throws while looking up an image by that name. Panes have a fixed width (`SettingsMetrics.paneWidth`) so hints wrap instead of widening the window. Text-holding widths (`paneWidth`, `fieldWidth`, `numberFieldWidth`) scale with `Typography.scale`, the measured width of sample text in the configured font relative to the 13pt system font; point size alone undercounts wide families such as Menlo.
   - Grid layout: text fields need a fixed width, not a minimum one. A flexible field leaves the grid's column widths open, and the grid then measures rows at one width and draws them at another, unevening the spacing. The grid is `fixedSize` vertically so any spare height stays below it instead of spreading between rows, and single-line texts that may truncate (the settings path) set `lineLimit(1)`. Labels, checkboxes and fixed hints are `fixedSize`: a hint spanning the control and accessory columns would wrap at the widest control's width, well short of the pane's edge, because cells spanning columns do not widen them (a flexible spanning cell changes nothing, and a flexible accessory cell widens the columns only after the grid has measured the hint, leaving gaps under it). Fixed hints are therefore one short line; only text from elsewhere (status, warnings, errors) passes `wraps: true`. Steps put their extra buttons (Remove, Write Again, Copy Settings) beside them in a `fixedSize` HStack, not in an accessory column, which long hints spanning both columns would widen. `NumberField` is `fixedSize` too, or the grid squeezes its unit and wraps it mid-word. Once the config matches, Write Again (`AeroSpaceSync.update(rewritingBlock: true)`) writes the managed block anyway, which also moves a matching gap outside the block into one, and validates and reloads like an update. ### Coverage limits

- AeroSpace `fullscreen` respects outer gaps unless invoked with `--no-outer-gaps`.
- Floating windows are outside the tiling tree; gaps do not apply. Native green-button zoom sizes them to `visibleFrame` and they extend under the sidebar.
- macOS native fullscreen (`macos-native-fullscreen` or the green button) opens a separate Space and ignores gaps. `.fullScreenAuxiliary` lets the sidebar draw over it; it overlaps rather than displaces the app.

## Gotchas

- `HostedSidebar` in `ArrivalScrollTests.swift` checks arrival offsets with uniform cards in a 300×600 alpha-zero `TestPanel`, constructing `SidebarPanelContent` directly without `SidebarPanelController`, its background panel or the full-height strip. It does not reproduce the launch offset drift caused by scaling the list's `ScrollView`, even with varying card heights and reply buttons. The cause of the difference is not isolated; do not assume transparency alone explains it or treat a passing hosted test as launch-regression coverage. Keep the structural guard `contentGrowsOutOfItsCornersOnTheScreenEdge`. A replacement behavioral test must fail when the scroll-view scale is restored and pass without it; any variant that shows a panel takes `.showsWindowsOnScreen` and runs only with `AEROSPACE_SIDEBAR_SCREEN_TESTS=1`.
- Hosted arrival-scroll assertions wait for SwiftUI to observe the current arrival count, an idle scroll phase, and stable clip bounds and content extent. Long gaps between main-actor samples do not count as stability. Initial readiness must succeed within 30 seconds; subsequent arrival waits retain their ten-second bound and geometry tolerances. Two matching offset samples alone can accept a position before the arrival is rendered.
- `~/.config/aerospace/aerospace.toml` is generated. Never edit it directly; edit `~/.dotfiles/mac-apps/aerospace/base.toml` or `~/.dotfiles/mac-apps/aerospace/configs/<profile>.toml`, then regenerate.
- The generator appends profile TOML sections after `base.toml`, and `[gaps]` already lives in `base.toml`. A `[gaps]` table in a profile file produces a duplicate-table TOML error. The sidebar's gap lives in the managed block inside `base.toml`'s `[gaps]`; the generator copies the block from the current generated config instead, so the sidebar's side and width survive regeneration.
- `base.toml` binds `alt-f = 'fullscreen'` (all profiles). Do not add `--no-outer-gaps`; it makes fullscreen windows cover the sidebar. In the generated file this binding appears below the `# --- Profile: <name> ---` marker because profile bindings are injected directly after `[mode.main.binding]`; it is not profile-specific.
- Monitor names differ between profiles. Patterns referenced in `configs/*.toml`: `^MAG321.*`, `DELL U3417W`, `DELL U3415W`, `^LG.*`, `EM160TP.*`, `Z1-7`, `built-in`, `secondary`. The gap uses `main` so it follows whichever display is main in every profile; name-based patterns would not.
- Tests create real `NSPanel`s and need a window-server session. Tests that use the real primary screen are disabled when `NSScreen.screens` is empty.
- Tests run on the user's desktop, so test windows must stay out of the way. A window that becomes key moves the user's keyboard focus to the test process, whatever its activation policy (titled windows become key as soon as they are ordered in); an opaque one covers the screen and takes clicks. AppKit pulls titled windows back onto a display when they are ordered in, so off-screen frames do not help. Order in only `TestPanel`s (`TestWindows.swift`: never key, `alphaValue` 0, still `isVisible`), build Settings with `SettingsWindowController.forTesting` (its `panelType` seam) and the sidebar with `SidebarPanelController.forTesting` (transparent panel), and never call `makeKey()`. Suites that create windows take `@Suite(.leavesDesktopAlone)`, which fails a test that ends with a visible window that is opaque on a display, titled and able to become key, or key. It checks window state rather than key notifications: the test process runs no event loop, so AppKit never hears that the window server moved keyboard focus. Only tests that need the window server to find a window (`transparentListAreaRetainsMouseEvents`, `realFontPanelReachesTheScreenWhileTheAppIsInactive`) show one, non-key and briefly, tagged with `NSUserInterfaceItemIdentifier.windowServerProbe` so the trait skips it. They flash in front of the user's work, so they take `.showsWindowsOnScreen` and run only with `AEROSPACE_SIDEBAR_SCREEN_TESTS=1`, which CI sets; local `just test` and `just coverage` leave them out. Never show a real system panel (the shared color or font panel) from a test without that trait: a `TestPanel` stands in for it (`SettingsColorWell.show(_:placing:)`, `closePanel(of:panel:)`), and never loop the test suite on the user's machine.
- Tests pretend screens (`targetVisibleFrame`, `sidebarScreenFrame`) that can be larger than the display of the machine running them; CI's is shorter than 900 pt. AppKit constrains windows to the real displays: it moves a borderless window taller than the display it overlaps down to the display's bottom edge, and a titled one onto the display as it is ordered in (measured on macOS 26.6). `TestPanel` and `TestSidebarPanel` (`SidebarPanelController.forTesting`, through its `panelType` seam) therefore return frames unconstrained (`constrainFrameRect(_:to:)`); a window a test makes must be one of them before its frame is asserted.
- Tests must never call `NotificationCenterMonitor.start()` with `SystemAccessibility` or bind `SidebarApp.controlSocketPath`: the first prompts for Accessibility and moves real NotificationCenter windows, the second collides with the running app. Inject `FakePlatform` and a `/tmp` socket path (short: `sockaddr_un` paths are limited to 104 bytes).
- Pass `FakeUserInput` (`RecentUserInputTests.swift`) to `NotificationHistoryOpener` and to `NotificationCenterMonitor(userInput:)` in tests where a late history panel can occur. `RecentUserInput.system` reads the session's real input and installs a local event monitor, so typing or scrolling at the desk while tests run would make a late panel count as the user's. To test what the sidebar's own input does, build `RecentUserInput` from `RecentUserInput.secondsSince(_:uptime:sessionAge:receivedAt:)` and a `ReceivedInput` fed through `record(_:at:)`.
- Tests must never start a `NotificationDatabaseMonitor` on the real database or `UserDefaults.standard`: it would list the user's notifications and move the stored read position. Use `NotificationDatabaseFixture` (`NotificationDatabaseTests.swift`), which builds a database with the same schema in a temporary directory and memory-only preferences, and pass its database to `SidebarAppDelegate(notificationDatabase:)` and its defaults through `makeDatabaseMonitor`. Preference consumers take `Preferences`; production uses `UserDefaults` and test fixtures use `InMemoryPreferences`. Do not create test suites in `~/Library/Preferences`: removing a persistent domain leaves an empty plist on macOS. The delegate owns the one `NotificationDatabase` and hands it to both the monitor and `makeOnboarding`, so a delegate built without it reads the real database.
- Tests must never run `SystemSettingsNotificationSwitch` with its default adapters, which open and click the real System Settings. Pass `FakeSystemSettings.makeSwitch()` or `FakeAppNotificationSwitch`, and read preferences from `NotificationPreferencesFixture` (a temporary home folder).
- Tests must never write `NSPasteboard.general`, the user's clipboard: restoring only its string loses everything else on it. `AeroSpaceSync` copies through its `copy` closure, which `AeroSpaceSync.fake` and `AeroSpaceSyncTests.sync()` make a no-op; a test of the copy itself passes `AeroSpaceSync.copying(to:)` an `NSPasteboard.withUniqueName()` pasteboard and calls `releaseGlobally()` on it afterwards.
- A shell or agent usually lacks Full Disk Access, so the notification database and usernoted's preferences do not open from it. To inspect them, push a notification whose `--run` command writes what it reads to a file and click its card: the command runs as the sidebar's child process and inherits its access.
- Debug-level `Logger` messages build their text in closures that never run while debug logging is off, which is always the case in tests, so they count as uncovered functions. Log each interception decision once at info level rather than per sweep at debug level. Watch the live log with `log stream --level info --predicate 'subsystem == "com.alexgorbatchev.aerospace-sidebar"'`. `OSLogPreferences` in `Resources/Info.plist` persists that subsystem's info level (the system default keeps info only in memory), so `log show --info` also covers past events; a message repeated per sweep would fill the store, which is one more reason to log each decision once. Each notification handed over to a card logs being hidden, every action performed on it, its close, and how it left NotificationCenter. Create loggers with `Logger(category:)` (`Logging.swift`): only the app bundle logs under that subsystem, and every other process running `SidebarKit`, such as the test runner, logs under `com.alexgorbatchev.aerospace-sidebar.tests`.
- Never block Swift's cooperative thread pool (socket `read`/`accept`/`write`, `Process.waitUntilExit`, `Task.detached` around blocking work). The pool is about as wide as the CPU count; on GitHub's 3-core runner, socket tests blocked every thread and the servers they waited on never ran, so CI hung with no output. Run blocking work through `onBlockingQueue` (`SidebarProtocol/BlockingQueue.swift`). `just test` and `just coverage` set `LIBDISPATCH_COOPERATIVE_POOL_STRICT=1` (one pool thread) so such deadlocks reproduce locally; CI runs tests under `script` with step timeouts so a hang shows the last test that started.
- Never change process-wide state such as signal dispositions on a path tests run in process: all three test targets share one test process, so it would leak into every later test. For example, ignoring SIGPIPE would keep tests from noticing a socket without `SO_NOSIGPIPE`. The CLI ignores SIGPIPE only in `SidebarCLI.runProcess` (called from `main.swift`), so output to a pipe whose reader has exited fails with EPIPE and exits `EX_IOERR` (74) with `output_write_failed` instead of dying with status 141. Its test is a Swift Testing exit test (`#expect(processExitsWith:)`), which runs it in a child process. In agent mode every failure is one `ERR: <code>: <detail>` line: ArgumentParser errors use `usage` (exit 64, `message(for:)` without the usage block), payload errors `invalid`, and other unexpected errors `failed`. Only help and the JSON dump use `fullMessage`.
- While an alert's reply field is open, NotificationCenter holds back every new notification, and it keeps the alert when its app removes it. If the posting process is gone by then (alerter timing out or killed), Close only collapses the field and the alert can never be closed. Restart NotificationCenter (`killall NotificationCenter`; launchd restarts it and the sidebar reattaches) to clear it. The sidebar closes the field again when a reply it sends fails (item 4, **Choices.**), but an alert whose undeclared choice opened a field returns on screen with the field open, and test alerts hit it: answer or close an alerter Reply alert before its `alert_timeout`.
- Killing `swift test` (Ctrl-C, `timeout`) leaves its `swiftpm-testing-helper` child running, and that process keeps the tests' real sidebar panels on screen. After interrupting a run, `pkill -f swiftpm-testing-helper`.
- Window-server tests such as `SidebarPanelControllerTests.transparentListAreaRetainsMouseEvents` (with `AEROSPACE_SIDEBAR_SCREEN_TESTS=1`), and `ArrivalScrollHostedTests`, which wait for real scroll animations in a hosted `SidebarView`, fail while the screen is locked: the lock's shield windows sit above every window, so hit tests find them, and the hosted list's scrolls never settle (observed on macOS 26.6). Unlock before running `just test` or `just coverage`.
- Notification cards sit on `.regularMaterial` under their severity tint. The tints are translucent, so without the material a card sliding up over a removed one shows the removed card's text through it even though `zIndex` (from `drawingOrder`) draws it on top.
- ViewInspector evaluates a view's body when searched, not when `inspect()` is called, so assert pre-action text before tapping buttons that change it.
- Do not use SwiftPM resources (`Bundle.module`) in `SidebarKit`. The generated accessor looks for the resource bundle at the `.app` root, where codesign rejects it, then at an absolute `.build` path, and calls `fatalError` when neither exists. Ship files through `Resources/` and the `bundle` recipe, and pass their directory in (`AppIconFont.bundled(in:)` in the app, the repository's `Resources/` path in tests).
- `NSColorWell(style:)` is a class factory that returns a plain `NSColorWell`, also when called on a subclass, so `SettingsColorWell` is made with `init(frame:)` and its `colorWellStyle` set afterwards; overrides on an instance from the factory never run.
- `swiftc` 6.3 crashes on an immediately called `#require` result (`try #require(closure)(argument)`); bind the result first.
