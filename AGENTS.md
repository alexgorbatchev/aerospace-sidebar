# aerospace-sidebar

A permanent, always-visible sidebar on the macOS main display that tiled windows never cover. AeroSpace reserves the screen strip; this project supplies the window that occupies it. The sidebar replaces macOS notification banners and NotifyMeHow: it intercepts native notifications and lists them, together with notifications pushed by the `aerospace-sidebar` CLI and `aerospace-sidebar://` URLs.

## Commands

Swift package (`Package.swift`) driven by `justfile`:

- Build and relaunch the app bundle: `just run`. It quits NotifyMeHow first (`just quit-notifymehow`) so only one app hides banners. `just stop` quits the sidebar gracefully; `just bundle` only builds `.build/AerospaceSidebar.app` and `bin/aerospace-sidebar`.
- CLI: `just cli <args>`, agent mode `just cli-ai <args>` (the CLI's `run`/`run-ai` equivalents; `run` launches the app)
- Push sample notifications through every path (CLI, URL scheme, native `osascript`), one per severity, plus native alerts with an action, an action menu and a Reply button (`alerter`, `brew install vjeantet/tap/alerter`, sent as Script Editor like `osascript`; each waits in the background until answered, closed or `alert_timeout` seconds pass): `just test-notifications [alert_timeout]` (default 600)
- Fill the list with distinct notifications that never stack, to check scrolling: `just fill-notifications [count]` (default 20)
- Tests: `just test`
- Coverage gate: `just coverage`
- Re-prompt for Accessibility: `just reset-permissions`
- Replace the vendored sketchybar-app-font with a release: `just update-app-font <tag>` (downloads `sketchybar-app-font.ttf`, `icon_map.json` and `LICENSE`, writes the tag to `VERSION`)
- Release archives into `dist/` (what the release workflow runs): `just release-archives <version>`. Set `AEROSPACE_SIDEBAR_SIGNING_IDENTITY=-` for an ad-hoc build like CI; note that it replaces `.build/AerospaceSidebar.app`, so run `just run` afterwards to restore the Developer ID build.

CI (`.github/workflows/ci.yml`) runs `just coverage` on `macos-26` for pushes to `main` and pull requests. `.github/workflows/release.yml` runs on `v*` tags: coverage gate, `just release-archives`, then `gh release create` with `AerospaceSidebar_<version>_darwin_arm64.tar.gz`, `aerospace-sidebar_<version>_darwin_arm64.tar.gz` and `checksums.txt`. CI has no Developer ID, so release builds are ad-hoc signed and users re-grant Accessibility after each update. The README's installation section depends on these asset names.

`just coverage` runs `swift test --enable-code-coverage`, prints `llvm-cov report` for the test binary, and fails when line or function coverage over `Sources/` drops below 90% or when any `Sources/**/*.swift` file is missing from the report. It excludes `.build/` and `Tests/`. Test targets depend on both executables so each `main.swift` is compiled into the report; they stay unexecuted, so keep them minimal.

Always launch the bundle, not `swift run`. The bundle supplies the bundle id, `LSUIElement` (which AeroSpace relies on, see Architecture) and the `aerospace-sidebar` URL scheme. `just bundle` signs it with the Developer ID identity in `AEROSPACE_SIDEBAR_SIGNING_IDENTITY` (default `Developer ID Application: Alex Gorb (4XCZD8P4CJ)`); a stable identity keeps the Accessibility permission across rebuilds, while ad-hoc signing loses it every build.

Useful AeroSpace commands while developing:

- List monitors and their names (used in gap patterns): `aerospace list-monitors`
- Apply config changes: `aerospace reload-config`
- Regenerate the live AeroSpace config from dotfiles: `bash ~/.dotfiles/mac-apps/aerospace/select-config.sh <home|mobile|work>` (shell alias `aerospace-select`; restarts AeroSpace)

- `skills/aerospace-sidebar/SKILL.md`: agent skill for the CLI, printed by `aerospace-sidebar skill` as `alexgorbatchev/aerospace-sidebar` on branch `main`.
- `Tests/<Target>Tests/`: Swift Testing suites; `FakeElement`/`FakePlatform` in `SidebarKitTests/TestSupport.swift` stand in for the Accessibility API.

## Dependencies

- `TOMLDecoder` (dduan/TOMLDecoder): implements TOML 1.1, the version AeroSpace parses. Its `singleValueContainer()` decodes scalars only; decode arrays with `unkeyedContainer()` and tables with a keyed container or a nested `Decodable`.
- `swift-argument-parser`: CLI parsing. It lists only direct subcommands, so groups hide children (`shouldDisplay: false`) and render the full tree as their `discussion` (`CommandTree`). Its help wrapper breaks a line that fills the whole width, so tree lines are trimmed to width − 1, and help is rendered with `fullMessage(for:columns:)` at the same width. Help requests surface as its internal `CommandError`, not `CleanExit`; `ArgumentParserToolInfo` is not an exported product, so tests decode `--experimental-dump-help` JSON with local types.
- `swift-toml` (mattt/swift-toml, `import TOML`): reads and writes the app's own `config.toml` (TOML 1.0, Codable both ways). TOMLDecoder stays for AeroSpace's TOML 1.1 config. Both libraries export a type named `TOMLDecoder`; import only one per file.
- `PermissionFlow` (jaywcjlove/PermissionFlow): the Permissions group's Accessibility and Full Disk Access steps open the privacy pane through `PermissionFlowController.authorize(pane:)`, which shows a floating panel under System Settings from which the user drags the app into the list; status comes from its `PermissionStatusRegistry`. Its own Full Disk Access check probes unrelated protected paths, so `PermissionFlowGuide` registers `NotificationDatabaseAccess` (does the notification database open) for `.fullDiskAccess`. It ships a SwiftPM resource bundle with the panel's localized strings, `PermissionFlow_PermissionFlow.bundle`, and looks it up under `Bundle.main.resourceURL` without touching `Bundle.module`; `just bundle` copies it into `Contents/Resources`, never the `.app` root. The panel's views are internal: only its locale, the suggested `.app`s and the launch anchor are configurable.
- `ViewInspector` (tests only): drives SwiftUI controls in tests. SwiftUI's `NSHostingView` exposes no accessibility children in a test process, so `accessibilityPerformPress()` cannot reach SwiftUI buttons.

## Architecture

macOS has no public API for reserving screen space (no AppBar or strut equivalent). Only the menu bar and Dock shrink `NSScreen.visibleFrame`, which native zoom and Sequoia-style tiling use. The design therefore splits responsibilities:

1. **Space reservation: AeroSpace per-monitor outer gap.** Tiled windows on the target monitor stop short of the strip:
   ```toml
   [gaps]
   outer.<side> = [{ monitor."<pattern>" = <sidebar-width + 5> }, 5]   # 5 = existing default on other monitors
   ```
   Monitor patterns use the same syntax as `workspace-to-monitor-force-assignment`: `main`, `secondary`, a 1-based left-to-right index, or a case-insensitive regex substring of the monitor name. The last array element is the fallback.

   The sidebar targets `monitor.main` (System Settings → Displays → "Use as: Main display") on the edge set by `[sidebar] side` (default `right`). `[sidebar]` in the app's `config.toml` is the single source of side and width; `SidebarPanelController` re-pins whenever they change. Never hardcode the width elsewhere and never derive it from the AeroSpace config. AeroSpace must reserve the same strip: the `main` entry of `outer.<side>` minus that side's trailing fallback equals the width, so the regular 5pt gap stays between the sidebar and tiled windows. `AeroSpaceConfigEditor.analyze` compares the AeroSpace config (located like AeroSpace does: `~/.aerospace.toml` or `${XDG_CONFIG_HOME:-~/.config}/aerospace/aerospace.toml`, error if both exist) with the saved `[sidebar]`: a missing or different strip on the sidebar's side, or a `main` strip on the other side, is a mismatch. The fix rewrites a managed block (`# >>> aerospace-sidebar …` to `# <<< aerospace-sidebar <<<`) that owns `outer.left` and `outer.right` inside the gaps table; it keeps other monitors' entries and both fallbacks, puts the `main` entry first on the sidebar's side and drops a strip-reserving `main` entry on the other. A config without the block has its `outer.left`/`outer.right` lines moved into one; the comment lines right above them and comments after their values move above the block. TOML forbids a second `[gaps]` table, and a separate `[gaps.outer]` table collides with `outer.top`/`outer.bottom` dotted keys, so the block holds only the two assignments. A missing float rule is appended with an `# Added by aerospace-sidebar` comment. `AeroSpaceSync.sync()` applies the fix unless the config already matches or is missing: at launch, whenever the AeroSpace config changes on disk (`FileWatcher` on the file and its directory, reporting after 1 s without changes), and on every `[sidebar]` change (Save or a hand edit of `config.toml`). It queues a change that arrives mid-update and reports the result as `AeroSpaceSync.message` in Settings › Sidebar. Generated configs are edited too: a regeneration that drops the block is repaired after it. `AeroSpaceSetup.apply` keeps one backup (`aerospace.toml.bak`), validates with `reload-config --dry-run` and reloads only while AeroSpace (`bobko.aerospace`) runs, because the CLI talks to the running app and a failed check would otherwise restore the original. The delegate creates `AeroSpaceSync` at launch and hands it to the Settings window, so tests must inject one with a temporary home (`makeAeroSpaceSync`, `AeroSpaceSync.fake`, `AeroSpaceSetup.forTesting`), or launching and sidebar changes would edit the real AeroSpace config. The dotfiles `base.toml` holds the same block, and `select-config.sh` keeps the generated config's block when it regenerates and writes atomically.
2. **Sidebar window: self-positioning, always-on-top panel.** AeroSpace cannot position floating windows from config, so the sidebar sets its own frame to the reserved strip on `NSScreen.screens.first` (the menu-bar screen, which is AeroSpace's `main`). It uses `visibleFrame`, the same rect AeroSpace pads with outer gaps. Window behavior:
   - Borderless `NSPanel` subclass (`SidebarPanel`) with `.nonactivatingPanel`, `level = .statusBar`
   - `SidebarPanel` overrides `canBecomeKey` to accept key status only while handling a mouse-down on the panel (`NSWindow.currentEvent`). Borderless windows refuse key status by default, so without the override clicks never focus the sidebar and keyboard input (text fields, shortcuts) never reaches it. An unconditional `true` steals keyboard focus: once launching finishes AppKit makes the first visible window that can become key the key window (`_sendFinishLaunchingNotification`), and it picks another when a key window such as Settings closes. `.nonactivatingPanel` lets it become key without activating the app. Keep both.
   - Clear All and Settings (⌘,) are compact round icon buttons (`ExpandingIconButton`) in the top corner on the sidebar's screen edge, Settings outermost; there is no header. Under the pointer a button widens into a capsule that shows its title beside the icon (away from that edge, so the icon stays put) and turns white. `SidebarPanelContent` reads the side from `SettingsStore` in its body so the view follows side changes live. Each card's dismiss button is the same control, shown only while the card or the button is hovered, overhanging the card's top-trailing corner and opening its label leftward. The saber border is switched off for now (`showsSaberBorder` environment value, default false) and kept for later use; its unused, disabled code is intentional, so do not report or delete it. Switched on, a hovered card or button traces its edge with `SaberBorder`: a faint outline, and a beam that runs once around it in `SaberBeam.duration` each time the pointer arrives, growing out of the outline's point nearest where the pointer entered while it fades in, and fading out as its head runs on past that point (`SaberBeam.fade`; `SaberBlade` is `Animatable` so the fade follows the animated head), so neither end of the lap looks cut off (`.saberBorder` keeps that entry in screen space, so a widening icon button does not move it), clipped to the shape, a pale core inside a glow of the severity's color or the system accent (a core in the color itself vanishes into a high or critical card's matching stroke). The beam is the outline trimmed by arc length (`SaberTrail`, `Path.trimmedPath`), so it keeps one speed on long and short edges; a conic gradient would crawl along the middle of a long edge and race through the corners. Reduce Motion leaves only the outline.
   - Clicking a card plays a press (scale down) and a release (`PressableButtonStyle`, sequenced by `PressSequence`): the press always finishes before the release starts, however fast the click. The action runs as the release starts, so the card's fade-out plays alongside it; a release outside the card cancels the action. Option held as the mouse goes up (`NSEvent.modifierFlags`) runs the style's `alternateAction` instead, which on a card dismisses it without acting, like its dismiss button; the card's help says so whenever a click does more than dismiss. `NSApp.currentEvent` would name the mouse-up only while AppKit dispatches it from its queue, which tests cannot drive without deadlocking SwiftUI's mouse tracking, so tests pass `modifierFlags`.
   - `SidebarAppDelegate.makeMainMenu()` installs a main menu with only an Edit menu (Undo, Redo, Cut, Copy, Paste, Select All, sent to the first responder). An `LSUIElement` app shows no menu bar, but key equivalents such as ⌘C and ⌘V reach text fields only through main menu items, so without it Settings' fields ignore them. It has no Quit item, which would make ⌘Q quit from every Settings group.
   - Quit Sidebar lives in Settings › General (⌘Q while that group is shown) and calls `NSApplication.terminate`; `LSUIElement` apps have no menu bar, so this is the only in-app quit.
   - `collectionBehavior = [.canJoinAllSpaces, .stationary, .fullScreenAuxiliary, .ignoresCycle]`
   - `hidesOnDeactivate = false`
   - The panel is nearly invisible (`isOpaque = false`, 1% black background, `hasShadow = false`): WindowServer passes mouse events through fully transparent pixels before view hit testing, so the backing keeps scrolling continuous across card gaps and margins. Cards and buttons draw on `.regularMaterial` with `floatingShadow()` to separate them from what is behind. The hosting view is the content view directly.
   - Re-pin the frame on screen-configuration changes (`NSApplication.didChangeScreenParametersNotification`); hide the panel when no screen exists.
3. **Keep AeroSpace from managing the sidebar.** AeroSpace 0.21 (`isWindowHeuristic` in `AxUiElementWindowType.swift`) classifies a window of an `.accessory` app with no close button as a popup. Popups are never tiled, never assigned to a workspace, never hidden on workspace switches, and never trigger `on-window-detected`. Keep the panel borderless and `LSUIElement = true`. A floated window would belong to one workspace and be moved offscreen when that workspace is hidden. `base.toml` still floats the bundle id as a fallback:
   ```toml
   [[on-window-detected]]
   if = 'test %{app-bundle-id} = com.alexgorbatchev.aerospace-sidebar'
   run = 'layout floating'
   ```

4. **Notification interception: Accessibility API on NotificationCenter.** `NotificationCenterMonitor` observes `com.apple.notificationcenterui` (`kAXWindowCreated`, `kAXValueChanged`, `kAXLayoutChanged`, `kAXFocusedWindowChanged`). Every event sweeps all of NotificationCenter's windows, never just the element the event names; sweeps repeat every 0.25 s while notifications are closing or stacks expanding, stop 1.5 s after the last event once settled, and give up 10 s after it. Observed macOS 26 behavior the code relies on, with the projects that report the same:
   - **One window.** Every banner and alert on screen sits in a single `AXWindow` titled "Notification Center" (subrole `AXSystemDialog`) under `AXHostingView` › group › `AXScrollArea` › group `AXNotificationListItems`. A banner arriving while another notification shows creates no window and only reports `kAXLayoutChanged` on itself (Tactile, SignalLadder).
   - **Subroles, matched exactly:** `AXNotificationCenterBanner` (temporary), `AXNotificationCenterAlert` (persistent), `AXNotificationCenterAlertStack`, `AXNotificationCenterBannerStack`. Other `AXNotificationCenter…` subroles exist, such as `…NextFocus` (AnyDoor).
   - **Stacks.** Persistent alerts from one app collapse into an `AlertStack` that exposes only the newest alert's texts and ends its description with ", stacked"; bursts posted milliseconds apart collapse the same way (SignalLadder). `AXPress` expands it into flat siblings: an `AXHeading` with the app name, `Confirm Show Less` and `Clear` buttons, and one `AXNotificationCenterAlert` per notification, each with its own UUID (macos-notification-cli, AriSweedler/dotfiles notif-center). The interceptor presses a stack at most once per 2 s (a second press collapses it) and handles the expanded alerts individually; stacks from apps in `apps_left_to_macos` stay collapsed. `BannerStack` groups entries in the history panel (OmniWM).
   - **History panel.** Opening Notification Center puts the history into the same window with the same subroles. The application element reports `AXExpanded` = true and the panel shows a button with `AXIdentifier` `widget-editor-button` (AnyDoor, OmniWM). While it is open the sweep touches nothing and moves hidden windows back; closing a history entry would delete it.
   - **Content.** Texts carry `AXIdentifier` `title`, `subtitle`, `body`, plus `header` and `date`, which are ignored (roycetech/applescript-core, talon-axkit). The `AXDescription` joins app name, title, subtitle and body; the app name is what precedes the exact texts (vorssaint-utils), else the first part. macOS's own notifications (Disk Not Ejected Properly) start with the title, get the source `macOS` and no click action. A description can lag behind its texts (a countdown body), so the exact match is not guaranteed.
   - **Localized words.** Action names (`Close`, `Show`, `Show Details`), the description separator (`、` in Japanese) and the ", stacked" suffix are localized. `NotificationCenterLabels` reads them from `/System/Library/CoreServices/NotificationCenter.app/Contents/Resources/Localizable.loctable` for the application's `AXPreferredLanguage` (AnyDoor, MeetingMute, NotificationNanny); some table values are plural dictionaries, not strings. Raw action names look like `Name:Close\nTarget:0x0\nSelector:(null)`.
   - **Interactive.** A plain notification offers only `AXPress` and the localized Show Details, Show and Close. `NotificationBanners.needsInteraction` treats any other action, any control other than a close button or a button named like those actions (text fields, Reply buttons, Options pop-ups), and any element with `AXIdentifier` `action_button` (agent-desktop) as interactive. Hovering an alert adds Close and Show buttons to it (SignalLadder). Alerts are judged like banners, so an alert without choices is intercepted. While `actionable_left_to_macos` is on (the default), interactive notifications stay native and are listed with `shownByMacOS`; when it is off they are hidden and listed without their buttons. When unsure, leave a notification native: losing its buttons is worse than seeing a banner.
   - **Alert choices.** An `AXNotificationCenterAlert` with a UUID whose extra choices are all named actions (`NotificationBanners.choices`: macOS 26's "Privacy & Security" alert exposes `AXPress`, `Name:Show Details`, `Name:Allow…`, `Name:Close` and no buttons) is handed over whatever `actionable_left_to_macos` says: hidden but not closed, and listed with `SidebarNotification.nativeAlert` (identifier and choices). Named actions work while the window is off-screen. A button that only duplicates a choice (hover) is allowed; any other control (text field, pop-up, other `action_button`), more than `NotificationBanners.maxChoices` (2) choices, and every banner keep the interactive handling above. Hovering shows one choice as a button and two or more under an "Options" menu button whose items are not in the accessibility tree. An NSUserNotification actions menu (alerter's `--actions a,b --dropdown-label X`) also lists its header as a named action just before Close, the localized Show by default or the app's label; performing it closes the alert without an answer, and nothing tells it from a real choice, so alerts with three or more choices, which every menu with a custom header has, stay with macOS. `SidebarModel.presentAlerts` (published by each sweep, emptied on detach) decides whether a card shows its choices as push buttons; a choice runs `NotificationCenterMonitor.perform(.choice)`, a card click on a present alert runs `AXPress` instead of the card's action, and both dismiss the card on success. NotificationCenter reports `kAXErrorFailure` for Reply although the alert has opened its text field before the call returns, so an action also counts as performed when the alert's action names changed (Show Details becomes Hide Details; a gone alert has none). A dropped card (dismiss, Clear All, expiry, `max_count`) calls `alertsReleased()`, which sweeps; the interceptor closes handed-over alerts no card lists, waiting `choiceGrace` (2 s) after a performed choice so the alert can leave on its own. A card restored from `notifications.json` keeps its alert hidden after a relaunch. An alert the database listed first keeps native handling, and an alert that gains a control after a choice (Reply) returns on screen.
   - **Hiding.** Position changes on notification elements are ignored, and Close only takes effect after the ~1.3 s slide-in; nothing hides a single banner. A window is moved to (-5000, -5000) only when every notification in it is intercepted, and the move is read back (vorssaint-utils). A window holding a native notification stays on-screen at `nativeOrigin`: the window covers the main display from (0, 0) at layer 21, below the sidebar's `.statusBar` (25), and NotificationCenter draws notifications 16 pt inside the right edge of the visible frame (left of a Dock on the right, measured), so a right-side sidebar would cover them and take their clicks. The window moves left by the strip's width (`SidebarLayout.coverage(ofRightEdgeOf:)`), which keeps that 16 pt margin to the sidebar; NotificationCenter keeps that position and hit testing follows it until it discards the window, and the next window starts at (0, 0) again, so every sweep places it. `SidebarAppDelegate` sweeps again (`NotificationCenterMonitor.refresh()`) when the sidebar's side or width changes. Intercepted banners in that window show until their Close lands (MeetingMute accepts the same). Windows moved off-screen or beside the sidebar are moved back to (0, 0) on attach, while the panel is open and on quit, so always quit with `just stop` (Apple Event quit) rather than `kill`, which skips `applicationWillTerminate`.
   - **Closing.** Only an action named exactly the localized Close (or `AXCancel`), or a single close button, is used; two matches leave the notification alone (AnyDoor, MeetingMute). A substring match would press an app's own "Close Ticket".
   - **Identity.** Each notification's `AXIdentifier` is a UUID that survives stack expansion and NotificationCenter restarts (SignalLadder). Notifications with one are deduplicated by it alone, through `NotificationIdentities`; only those without one are compared by content within 10 s. Comparing identified notifications by content would drop real repeats, which `SidebarModel` stacks instead. `NotificationIdentities` keeps the newest 2000 UUIDs in `UserDefaults` (`notificationIdentities`), so a notification still on screen at a relaunch (left to macOS) is not listed again or stacked onto its card as a repeat, and a card dismissed before the relaunch stays gone. Tests pass `NotificationIdentities()` (memory only) or one on a fixture's defaults domain, never `.standard`, which `SidebarAppDelegate` defaults to.
   - **Lifecycle.** The monitor watches NotificationCenter's process for exit (`DispatchSourceProcess`) and reattaches with a doubling delay up to 30 s, because launch notifications missed relaunches (SignalLadder); it also reattaches after `NSWorkspace.didWakeNotification` (NotificationNanny). The observer's run loop source uses `.commonModes`, or events stall while a menu is open (SignalLadder), and AX calls time out after 1 s because NotificationCenter can take ~15 s to answer after a wake (NotificationNanny).
   - Focus/Do Not Disturb draws no banner at all; only the notification database (item 5) sees those notifications.
   NotifyMeHow, SignalLadder, vorssaint-utils and OmniWM are GPL; QuietYou, the AriSweedler, tim-hilde and volodymyr-xn dotfiles have no license. Use them as sources of facts only and never copy their code into this MIT project.
5. **Notification database: what no banner showed.** With Full Disk Access, `NotificationDatabaseMonitor` reads `~/Library/Group Containers/group.com.apple.usernoted/db2/db` read-only through the system `SQLite3` library and watches its `db-wal` with `FileWatcher`. Without Full Disk Access, opening it fails with "authorization denied"; the monitor logs that once and retries every 5 s, and Settings › Permissions offers Open Full Disk Access through PermissionFlow's drag panel. macOS lists an app in Full Disk Access, switched off, once it has tried to open a protected file, so after the first launch the user usually only flips the switch.
   - Schema (Apple-private, read the same way by AriSweedler/dotfiles notif-center and OmniWM): `app(app_id, identifier)` holds bundle identifiers; `record(rec_id, app_id, uuid, data, delivered_date)` holds one row per notification. `uuid` is 16 bytes and equals the notification's `AXIdentifier` (OmniWM). `delivered_date` counts seconds since 2001 and is empty or in the future for scheduled notifications. `data` is a binary property list whose `req` dictionary holds `titl`, `subt` and `body`.
   - Measured on macOS 26: usernoted writes a record to `db-wal` about 5–7 s after delivering it, so a notification without a banner reaches the sidebar roughly 8 s after delivery (that write, the watcher's 0.2 s debounce and the 1 s grace). A notification closed before then, which includes every banner the interceptor closes, is never written. The `database` log's "Read …" line gives both delays for each read.
   - Each new record waits 1 s for its banner, which is reported within about a second of delivery and so long before macOS writes the record; records whose UUID `NotificationIdentities` already holds are skipped, the rest are listed with the app's display name (`macOS` and no click action when no installed app has the bundle identifier) and their delivery time.
   - The newest record id read is kept in `UserDefaults` (`notificationDatabaseRecordID`), so notifications delivered while the sidebar was not running are listed at the next launch. The first launch starts from the newest record; a stored id above the newest record (a recreated database) starts over from it.
6. **Pushed notifications: two entry points with different trust.**
   - `aerospace-sidebar://notification/push?title=&subtitle=&body=&severity=&open=` (handled in `SidebarAppDelegate.application(_:open:)`). Any process, and any web page after the browser's confirmation prompt, can open it. Never let URLs carry commands; `open` accepts only `http`/`https`. The sender app (Apple Event `keySenderPIDAttr`) labels the notification, else `URL`.
   - Control socket `$(getconf DARWIN_USER_TEMP_DIR)com.alexgorbatchev.aerospace-sidebar.sock`: mode 0600 in the per-user temp directory, peer uid checked with `getpeereid`, one JSON `ControlRequest` per connection. Only this path may carry `run` actions. Set `SO_NOSIGPIPE` on every socket (`UnixSocket.disableSIGPIPE`); a client that disconnects early otherwise kills the app.
   - Click actions: `open` (LaunchServices), `run` (`$SHELL -lc` in the CLI's working directory, output discarded), `activateApp` for intercepted notifications; a card for a present alert presses the alert instead (item 4). Hovering a card shows `clickDescription`, including the full command. Alert choices are native push buttons inside the card's `PressableButtonStyle` button; they take their own clicks without pressing the card. VoiceOver sees each card as that one button and cannot press buttons nested in it: pressing one through accessibility runs the card's action instead. So the card's label children are ignored (each text would otherwise become an unnamed custom action), `NotificationCard.accessibilitySummary` is its label, the alert's choices and Dismiss (shown only under the pointer) are its `accessibilityActions`, and the nested choice buttons are hidden from accessibility.
   - Icons: `icon` (CLI `--icon`, URL `icon=`, at most 64 characters) is a sketchybar-app-font id, written `slack` or `:slack:` in any case. The font draws `:slack:` as one glyph through a ligature, so the card sets that text in `AppIconFont.family` at the caption size before the sender. `AppIconFont` checks ids against the bundled `icon_map.json`; an unknown id is not an error: the notification keeps no icon, stores the value as `invalidIcon`, and the card shows `Invalid icon: <value>` as a caption note styled like "Shown by macOS for its buttons". Notifications without an id, including intercepted ones, have no icon. One id can stand for several apps (`mail`), so the VoiceOver label is the id in words, not an app name.
   - Severity `low` < `normal` < `high` < `critical`: the list sorts by severity, then newest first, and drops the least severe, oldest entries beyond 200. `low` is dimmed, `high` orange, `critical` red.
   - Rules: `[[rules]]` tables (`SidebarSettings.Rule`) hold `source`, `title`, `subtitle` and `body` patterns, case-insensitive Swift `Regex`es searched anywhere in that field (empty matches anything, at least one is required), and an `action`: `hide` or a severity. `SidebarModel.add` runs every arriving notification, from any entry point, through `NotificationRules` before stacking: the first rule whose patterns all match sets its severity or drops it. Saved rules also restack the listed cards (`SidebarModel.apply(rules:)`): each starts over from the severity it arrived with, which a card keeps in `postedSeverity` while a rule shows another, then goes through the new rules like an arriving notification, so it moves to its new severity, stacks with a card that now shows the same content (the stack keeps its first card's posted severity), or goes when a rule hides it. A hidden alert is never listed, so the interceptor closes it like any alert no card lists; a hidden notification left to macOS still shows its banner. Loading refuses unusable rules like any invalid setting (`rules[1].title: …`), Save names them (`Rule 2 …`). Settings › Rules shows the rules in a full-width list with +, −, ↑, ↓ along its bottom edge (the window is inactive, so no drag reordering is relied on) and an empty-state line, then edits the selected rule in a group box below: its patterns (each with a help tag naming what it matches, under a note on the pattern format), one Then pop-up (Hide it, or List as one severity) and which listed notifications it matches, in space reserved for `RulesPane.matchLines` lines. Without a selection the editor's rows stay laid out but invisible, disabled and hidden from accessibility under a line saying what to do, so selecting a rule never resizes the window. The list and the editor share one width (the pane's own, inside its margins); the editor is a group box in `SettingsGroupBoxStyle`, whose padding (`SettingsMetrics.groupPadding`) is known, unlike the system style's, and its fields take what that padding and the widest label (measured in the configured font) leave, so the padding is the same on the left, at the top and on the right. These widths are computed, not measured from the layout: measuring the box or the list fed back through the note's wrapping, the pane's reported size and the window's, and hung the app in a layout loop. Its note sets `SettingsHint(columns: 1)`: a grid without accessories gets an empty third column, and its gap, from a hint spanning two. AppKit controls without text of their own, such as the pop-up, have no baseline, so their row centers the label (`SettingsRow(alignment: .center)`).
   - Stacking: `SidebarModel.add` folds a notification into a listed one with the same content (`hasSameContent`: source, title, subtitle, body, severity, icon, `invalidIcon`, action, `shownByMacOS`, `nativeAlert`, so cards for different alerts never stack). The entry keeps its id, takes the newer `receivedAt`, adds `occurrences`, and is re-inserted as the newest. `SidebarView` keys cards by id and `occurrences`, so a restack fades the old card out and inserts a new one instead of sliding it across the translucent cards between. This is separate from the interceptor's 10 s dedupe, which drops NotificationCenter's repeated reports of one banner; stacking counts real repeats.
   - Scrolling: the list hides the system scroller (`.scrollIndicators(.never)`; `.hidden` still shows legacy scrollers when a mouse is attached) and draws `ScrollIndicator` in the margin on the sidebar's screen edge (`SidebarView.screenEdge`, shared with the top buttons) from `onScrollGeometryChange`, dragging through `ScrollPosition`. Legacy scrollers draw a track and take their width from the cards. The list runs to the bottom of the visible frame and fades its top or bottom 48pt (`EdgeFadeMask`) while cards are hidden past that edge; scrolled to the end, `contentMargins` keeps 16pt under the last card.
   - History: `SidebarModel` saves the list through `NotificationStore` on every change (`FileNotificationStore`: `~/Library/Application Support/com.alexgorbatchev.aerospace-sidebar/notifications.json`) and drops notifications older than 24 hours on load and every minute, so a relaunch restores the list. Tests pass an in-memory store; `SidebarModel` has no default store so tests cannot write the real file.

7. **Settings.** `${XDG_CONFIG_HOME:-~/.config}/aerospace-sidebar/config.toml` holds `[sidebar] side (left|right), width (150…1000)`, `[notifications] replace_system, actionable_left_to_macos, apps_left_to_macos`, `[history] retention_hours (1…720), max_count (10…2000)`, `[font] name, size (8…32)` and `[[rules]]` (below). `SettingsStore` watches `config.toml` through `FileWatcher` (writes in place and atomic replacements alike) and applies valid edits live; an invalid file keeps the last valid settings and surfaces `loadError`. Launch at login is never stored there: macOS owns that state, and a stored copy would re-enable a login item the user turned off in System Settings.
   - The Settings window has a full-height sidebar of groups (`SettingsGroup`: General, Appearance, Sidebar, Permissions, Notifications, Rules, History) beside the selected group's pane, like System Settings, and no section headers. Settings opens on General from the gear button and on Permissions from the sidebar's Set Up… prompt (`SidebarAppDelegate.showSettings(_:)`). `NSSplitViewController` holds a sidebar item (a SwiftUI `List` with `.listStyle(.sidebar)`, fixed at `SettingsMetrics.sidebarWidth`, not collapsible) and the panes in an `NSTabViewController` with `tabStyle = .unspecified`, which switches them. `SettingsNavigation.selection` is the shown group: the list binds to it and the controller follows it, selecting the pane and titling the window after the group. The selected row names the pane, so the window draws no title (`titleVisibility = .hidden`, no title bar separator, `titlebarAppearsTransparent`, no toolbar; the split view otherwise draws a title bar background with a separator line over the panes, which the window's separator style does not remove); the title stays for VoiceOver and the window list. The window uses `.fullSizeContentView`; `BelowTitleBarController` frames the panes in its safe area (frames, not constraints, which would tie the window's size to the shown pane's). The list's rows use `[font]` through `SettingsSidebarLabelStyle`, and its width scales with `Typography.scale`: the sidebar style sizes its own icon column for the system's sidebar font, so a row in another font needs the style's icon column, sized in multiples of the font size (`sidebarIconWidth`, `sidebarIconSpacing`), to keep its icons aligned. Each pane copies the layout of simple-ptt's settings window (`src/settings_window` in github.com/alexgorbatchev/simple-ptt): a grid with right-aligned `Label:` cells, subheadline-style secondary hints under controls (13pt and 11pt at the default font size), 8pt spacing, 20pt margins, checkboxes rather than switches, 80pt number fields with `Stepper` arrows (at the default font size), and, on the groups that edit `config.toml` (Appearance, Sidebar, Notifications, Rules, History), a separator + status line + Cancel/Save bar; General and Permissions act immediately, so they have none. Sidebar also holds the AeroSpace rows (`AeroSpaceRows`: config file and the Update Config step), with no header between them; those act immediately on the saved side and width. Permissions holds everything the sidebar asks macOS for (Accessibility, Full Disk Access, launch at login), each with a hint saying whether it is required and why, and a Remove button beside its step: `tccutil reset Accessibility|SystemPolicyAllFiles <bundle id>` for the privacy permissions (always shown, since an entry macOS no longer recognizes after an update reads as not granted), `SMAppService.unregister` for the login item. General holds the settings file and Quit. The draft panes share one `SettingsEditor`, so Save on any of them saves every group's edits. Setup steps (Permissions, AeroSpace) start with a status circle (green `checkmark.circle.fill` when done, empty `circle` otherwise) followed by the step's button while not done; a finished step shows the checkmark alone. Edits stay in `SettingsEditor.draft` until Save; Cancel and closing the window discard them. The draft font is the exception: it is previewed immediately through `SettingsStore.preview(font:)` (in memory only, never written to `config.toml`), and Save or Cancel ends the preview.
   - Unlike simple-ptt, which switches to the `.regular` activation policy while Settings is open, Settings is a non-activating `NSPanel` at `SettingsWindowController.level`, one above the sidebar's `SidebarPanelController.level` (`.statusBar`), so it stays above other apps' windows and the sidebar until closed, ordered in front with `orderFrontRegardless()`. Opening it from the closed state centers it on the sidebar's screen (`SidebarPanelController.primaryScreenVisibleFrame`); `NSWindow.center()` would use `NSScreen.main`, the screen with keyboard focus, which an app that never activates does not control. Size changes keep it centered until the user moves it, then keep its top edge. While it is open, opening it again leaves it where it is. The exception is System Settings, where the Permissions steps send the user: while it is the frontmost app, `SettingsWindowController.follow(frontmostApp:)` drops Settings to the normal level and orders it behind, so it does not cover the permission lists and their switches, and raises it above the sidebar again when another app comes forward. A level change alone keeps the window's place in the stack, so both orderings are explicit. Switching the policy would make AeroSpace re-classify the sidebar panel as a window (see item 3), and `NSApp.activate()` from a background app is only a request since macOS 14. An `NSPopUpButton` opens in Settings while another app is frontmost (checked with a real click on the Rules pane's Then pop-up). SwiftUI's menu and segmented `Picker`s draw through AppKit without passing a font on, so they stay in the system font whatever `[font]` says; `PopUpPicker` wraps `NSPopUpButton` and sets the button's and its menu's `font`.
   - Fonts: `[font] name` is a font family as Font Book lists it (empty = system font) and `size` is the body size. `Typography` derives every text style from it, keeping each `NSFont.TextStyle`'s proportion to `.body` (and its bold trait), so the default 13pt reproduces the system styles. `.typography(store)` on the sidebar's and each Settings pane's root view reads `SettingsStore.font` (the preview while Settings edits the font, else the saved font; `observeFont` reports its changes), clamps the size to the valid range, publishes `\.typography` and sets the body font for unstyled text and control labels; views pick other styles with `typography.font(.callout)` and friends instead of SwiftUI's `.font(.callout)` or fixed sizes. Push buttons are drawn by AppKit and ignore the inherited font; it only applies when set on the `Text` label itself (not through a wrapper view), so title buttons with `Button(_:font:action:)`. Settings › Appearance › Choose… opens the macOS font panel through `FontChooser`, which makes itself `NSFontManager.target` (the default target is the key window's first responder, which this app rarely has), sets the panel's `hidesOnDeactivate = false` (the window server keeps hide-on-deactivate panels off screen while their app is inactive, although AppKit still reports `isVisible`), places it beside Settings on the side away from the saved sidebar side, or the other side when that does not fit (AppKit's default position can be off-screen, and the sidebar floats above the panel), limits the panel to collection/face/size, and writes the picked family and size into the draft; the system font's hidden family (`.AppleSystemUIFont`) becomes an empty name. A family that is not installed renders the system font (SwiftUI's `Font.custom` would silently fall back to Helvetica), and Settings reports it. On font changes the Settings window runs `layoutSubtreeIfNeeded()` on its panes, shown or not, because pending SwiftUI updates only apply during a layout pass, so each pane reports its size for the new font.
   - The window fits the largest pane and the group list, so switching groups never resizes it; every pane fills it, grid at the top and button bar at the bottom. `SettingsPage` measures its grid and button bar with `onGeometryChange` and reports the sum through the `reportPaneSize` environment closure, and `SettingsSidebar` reports the list's content height and insets through `onScrollGeometryChange`. `NSHostingController` updates `preferredContentSize` lazily, without KVO or `preferredContentSizeDidChange(for:)` on a parent that is not a window, so pane hosting controllers use `sizingOptions = []` and report nothing themselves. In the running app the panes report after the event that opens the window (in tests, synchronously), so `sizeWindow` waits until every pane has reported and centers the window on that first size rather than in `show()`. It measures what the window adds around the panes and the list (title bar, toolbar, sidebar and its margins, which differ between macOS versions) from the current layout, which takes a window larger than those: assigning `contentViewController` shrinks the window to the empty split view, so `init` sets `measuringSize` after it. Measuring a degenerate window moved Settings off its screen. Each pane's root is `SettingsPaneHost<Pane>`: with the environment closure in the hosting controller's generic arguments, `NSStringFromClass` returns nil for it and `NSTabViewItem(viewController:)` throws while looking up an image by that name. Panes have a fixed width (`SettingsMetrics.paneWidth`) so hints wrap instead of widening the window. Text-holding widths (`paneWidth`, `fieldWidth`, `numberFieldWidth`) scale with `Typography.scale`, the measured width of sample text in the configured font relative to the 13pt system font; point size alone undercounts wide families such as Menlo.
   - Grid layout: text fields need a fixed width, not a minimum one. A flexible field leaves the grid's column widths open, and the grid then measures rows at one width and draws them at another, unevening the spacing. The grid is `fixedSize` vertically so any spare height stays below it instead of spreading between rows, and single-line texts that may truncate (the settings path) set `lineLimit(1)`. Labels, checkboxes and fixed hints are `fixedSize`: a hint spanning the control and accessory columns would wrap at the widest control's width, well short of the pane's edge, because cells spanning columns do not widen them (a flexible spanning cell changes nothing, and a flexible accessory cell widens the columns only after the grid has measured the hint, leaving gaps under it). Fixed hints are therefore one short line; only text from elsewhere (status, warnings, errors) passes `wraps: true`. Steps put their extra buttons (Remove, Write Again, Copy Settings) beside them in a `fixedSize` HStack, not in an accessory column, which long hints spanning both columns would widen. `NumberField` is `fixedSize` too, or the grid squeezes its unit and wraps it mid-word. File rows (General's Settings file, Sidebar's AeroSpace config) share `SettingsFileRow`: the `~`-abbreviated path, truncated in the middle, with Show in Finder in the accessory column.
   - Update Config (Settings › Sidebar): edits the gap to match the saved `[sidebar]` (not the unsaved draft). Once the config matches, Write Again (`AeroSpaceSync.update(rewritingBlock: true)`) writes the managed block anyway, which also moves a matching gap outside the block into one, and validates and reloads like an update. It refuses layouts it cannot edit safely (multi-line arrays, tables with several monitors, an incomplete or misplaced block), offering Copy Settings instead. It never creates a missing AeroSpace config, because a config file without `[mode.main.binding]` drops AeroSpace's default key bindings.

### Coverage limits

- AeroSpace `fullscreen` respects outer gaps unless invoked with `--no-outer-gaps`.
- Floating windows are outside the tiling tree; gaps do not apply. Native green-button zoom sizes them to `visibleFrame` and they extend under the sidebar.
- macOS native fullscreen (`macos-native-fullscreen` or the green button) opens a separate Space and ignores gaps. `.fullScreenAuxiliary` lets the sidebar draw over it; it overlaps rather than displaces the app.

## Gotchas

- `~/.config/aerospace/aerospace.toml` is generated. Never edit it directly; edit `~/.dotfiles/mac-apps/aerospace/base.toml` or `~/.dotfiles/mac-apps/aerospace/configs/<profile>.toml`, then regenerate.
- The generator appends profile TOML sections after `base.toml`, and `[gaps]` already lives in `base.toml`. A `[gaps]` table in a profile file produces a duplicate-table TOML error. The sidebar's gap lives in the managed block inside `base.toml`'s `[gaps]`; the generator copies the block from the current generated config instead, so the sidebar's side and width survive regeneration.
- `base.toml` binds `alt-f = 'fullscreen'` (all profiles). Do not add `--no-outer-gaps`; it makes fullscreen windows cover the sidebar. In the generated file this binding appears below the `# --- Profile: <name> ---` marker because profile bindings are injected directly after `[mode.main.binding]`; it is not profile-specific.
- Monitor names differ between profiles. Patterns referenced in `configs/*.toml`: `^MAG321.*`, `DELL U3417W`, `DELL U3415W`, `^LG.*`, `EM160TP.*`, `Z1-7`, `built-in`, `secondary`. The gap uses `main` so it follows whichever display is main in every profile; name-based patterns would not.
- Tests create real `NSPanel`s and need a window-server session. Tests that use the real primary screen are disabled when `NSScreen.screens` is empty.
- Tests run on the user's desktop, so test windows must stay out of the way. A window that becomes key moves the user's keyboard focus to the test process, whatever its activation policy (titled windows become key as soon as they are ordered in); an opaque one covers the screen and takes clicks. AppKit pulls titled windows back onto a display when they are ordered in, so off-screen frames do not help. Order in only `TestPanel`s (`TestWindows.swift`: never key, `alphaValue` 0, still `isVisible`), build Settings with `SettingsWindowController.forTesting` (its `panelType` seam) and the sidebar with `SidebarPanelController.forTesting` (transparent panel), and never call `makeKey()`. Suites that create windows take `@Suite(.leavesDesktopAlone)`, which fails a test that ends with a visible window that is opaque on a display, titled and able to become key, or key. It checks window state rather than key notifications: the test process runs no event loop, so AppKit never hears that the window server moved keyboard focus. Only tests that need the window server to find a window (`transparentListAreaRetainsMouseEvents`, `realFontPanelReachesTheScreenWhileTheAppIsInactive`) show one, non-key and briefly, tagged with `NSUserInterfaceItemIdentifier.windowServerProbe` so the trait skips it.
- Tests must never call `NotificationCenterMonitor.start()` with `SystemAccessibility` or bind `SidebarApp.controlSocketPath`: the first prompts for Accessibility and moves real NotificationCenter windows, the second collides with the running app. Inject `FakePlatform` and a `/tmp` socket path (short: `sockaddr_un` paths are limited to 104 bytes).
- Tests must never start a `NotificationDatabaseMonitor` on the real database or `UserDefaults.standard`: it would list the user's notifications and move the stored record id. Use `NotificationDatabaseFixture` (`NotificationDatabaseTests.swift`), which builds a database with the same schema in a temporary directory and its own defaults domain, and pass `makeDatabaseMonitor` to `SidebarAppDelegate`.
- Debug-level `Logger` messages build their text in closures that never run while debug logging is off, which is always the case in tests, so they count as uncovered functions. Log each interception decision once at info level rather than per sweep at debug level. Watch the live log with `log stream --level info --predicate 'subsystem == "com.alexgorbatchev.aerospace-sidebar"'`. `OSLogPreferences` in `Resources/Info.plist` persists that subsystem's info level (the system default keeps info only in memory), so `log show --info` also covers past events; a message repeated per sweep would fill the store, which is one more reason to log each decision once. Each alert handed over to a card logs being hidden, every action performed on it, its close, and how it left NotificationCenter. Create loggers with `Logger(category:)` (`Logging.swift`): only the app bundle logs under that subsystem, and every other process running `SidebarKit`, such as the test runner, logs under `com.alexgorbatchev.aerospace-sidebar.tests`.
- Never block Swift's cooperative thread pool (socket `read`/`accept`/`write`, `Process.waitUntilExit`, `Task.detached` around blocking work). The pool is about as wide as the CPU count; on GitHub's 3-core runner, socket tests blocked every thread and the servers they waited on never ran, so CI hung with no output. Run blocking work through `onBlockingQueue` (`SidebarProtocol/BlockingQueue.swift`). `just test` and `just coverage` set `LIBDISPATCH_COOPERATIVE_POOL_STRICT=1` (one pool thread) so such deadlocks reproduce locally; CI runs tests under `script` with step timeouts so a hang shows the last test that started.
- While an alert's reply field is open, NotificationCenter holds back every new notification, and it keeps the alert when its app removes it. If the posting process is gone by then (alerter timing out or killed), Close only collapses the field and the alert can never be closed. Restart NotificationCenter (`killall NotificationCenter`; launchd restarts it and the sidebar reattaches) to clear it. Nothing the sidebar does causes it, but it hits test alerts: answer or close an alerter Reply alert before its `alert_timeout`.
- Killing `swift test` (Ctrl-C, `timeout`) leaves its `swiftpm-testing-helper` child running, and that process keeps the tests' real sidebar panels on screen. After interrupting a run, `pkill -f swiftpm-testing-helper`.
- Window-server tests such as `SidebarPanelControllerTests.transparentListAreaRetainsMouseEvents` fail while the screen is locked: the lock's shield windows sit above every window, so hit tests find them. Unlock before running `just test` or `just coverage`.
- Notification cards sit on `.regularMaterial` under their severity tint. The tints are translucent, so without the material a card sliding up over a removed one shows the removed card's text through it even though `zIndex` (from `drawingOrder`) draws it on top.
- ViewInspector evaluates a view's body when searched, not when `inspect()` is called, so assert pre-action text before tapping buttons that change it.
- Do not use SwiftPM resources (`Bundle.module`) in `SidebarKit`. The generated accessor looks for the resource bundle at the `.app` root, where codesign rejects it, then at an absolute `.build` path, and calls `fatalError` when neither exists. Ship files through `Resources/` and the `bundle` recipe, and pass their directory in (`AppIconFont.bundled(in:)` in the app, the repository's `Resources/` path in tests).
- `swiftc` 6.3 crashes on an immediately called `#require` result (`try #require(closure)(argument)`); bind the result first.
